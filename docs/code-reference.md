# Chanakya AI Assistant — Full Code Reference

Every code file in the repository, explained. Generated by reading each file's actual
contents (not inferred from names) across the Node/Express backend, the IndicTrans2
Python microservice, the React/Electron frontend, and the dataset-building tooling.

**How to use this doc:** it's organized by subsystem, roughly in the order a request
travels through the app. Each `###` heading is one file, given as its path from the
repo root. A few sections call out files that look load-bearing but are actually dead
code (an earlier prototype RAG pipeline, a duplicate config module) — that's noted
explicitly wherever it applies, since it's easy to assume everything present is live.

## Top-level project files

### package.json
The npm-workspaces root, listing `frontend` and `backend` as workspaces. Its scripts
are the entry points a developer actually runs: `npm run dev` starts both the backend
API and the Vite frontend concurrently (via the `concurrently` devDependency), `npm run
build` builds only the frontend, `npm start` starts the built backend (which also
serves the compiled frontend as static files, per `app.js`), `npm test` runs the
backend's test suite, and `npm run ship` runs `scripts/ship.mjs` (not read in this
pass — a release helper).

### frontend/package.json
The Electron/React frontend's manifest. Its `build` block configures electron-builder:
app id `com.chanakya.ai`, product name "Chanakya AI", a pinned Electron version
(37.10.3) sourced from a local `.electron-dist/` cache rather than downloaded per
build, Windows-only NSIS installer output, `asar: false` (so the packaged app's files
stay inspectable/unarchived on disk), and an `afterPack` hook (`scripts/afterPack.cjs`,
covered below) plus two extra `node_modules` packages (`say`, `one-time`) explicitly
copied in since they're used only by the Electron main process, not bundled by Vite.
Dependencies mix UI libraries (React 19, Framer Motion, Zustand, Tailwind via
`postcss`/`autoprefixer`), 3D avatar libraries (`three`, `@react-three/fiber`,
`@react-three/drei`, `@react-spring/web`), in-browser AI (`@huggingface/transformers`
for local Whisper transcription), OCR (`tesseract.js`), and native Windows TTS
(`say`).

## Translator feature: IndicTrans2 integration

The Translator sidebar tab is a self-contained subsystem layered onto the rest of the
app rather than woven through it. A request to `POST /api/translate` passes
`requireAuth` then `translateLimiter` (15/min, keyed per authenticated user rather than
by IP, since every request on this desktop app shares one loopback address), has its
language codes and text validated against a shared allowlist, and — if the source
language is `"auto"` — is classified by a pure Unicode-script counter with no model
call involved. The actual translation always happens in a **separate local Python
process** (`indictrans-service/`, FastAPI + AI4Bharat's IndicTrans2 checkpoints),
reached over loopback HTTP exactly the way this app already reaches Ollama — it is a
second, independent local AI backend, not a feature of Ollama. Ollama/Qwen3 touches
translation in exactly one place: an optional, off-by-default fluency-polish pass over
IndicTrans2's *already-produced* output, whose own failure can never fail the request.
There is no LLM-based "intent detection" anywhere in this path — the Translator is
invoked only by an explicit UI action or an explicit API call, never inferred from a
chat message (see the note under `IntentClassifier.js` below for why that's a
different, unrelated subsystem).

### backend/src/routes/translate.js
Registers `POST /` (mounted as `/api/translate`) behind `requireAuth` and
`translateLimiter`. It validates `sourceLanguage` (any known code, or `"auto"`),
`targetLanguage` (any known code, never `"auto"` — there's no such thing as an
auto-detected destination), and `text` (1 to `config.translate.maxChars`, default 5000,
characters) via `requireEnum`/`requireString`. If the source is `"auto"`, it calls
`detectLanguage()` and 400s with a clear message if detection isn't confident enough
rather than guessing. If source and target end up identical (including after
auto-resolution), it short-circuits to `{ translation: text }` with no provider call at
all. Otherwise it calls `translateText()` and returns `{ translation }`, logging only
structured metadata (source/target/char-count/duration/engine) — never the text itself
— tagged with the request's correlation id. A thrown `TranslationError` maps to its own
`.status` (503 service down, 504 timeout, 400 bad pair, 502 provider failure); anything
else falls through to the app's generic error handler.

### backend/src/services/translationService.js
The orchestration layer: validate the pair (defense-in-depth re-check) → apply
`applyGlossary()` → POST to the IndicTrans2 microservice's `/translate` → optionally run
`postProcessTranslation()`. Exports `TranslationError` (a class carrying a client-safe
`.message` plus a server-only `.detail`, deliberately not embedding a `.status` in the
4xx sense since these are all 5xx-class provider failures the route itself decides how
to surface) and `translateText({text, sourceLanguage, targetLanguage})`. The internal
`callIndicTrans2()` helper posts JSON to `${config.translate.serviceUrl}/translate`
with an `AbortSignal.timeout`, maps the Python service's structured `{error_code,
detail}` error body to the right `TranslationError` (`MODEL_NOT_LOADED` → 503,
`UNSUPPORTED_PAIR` → 400, `EMPTY_OUTPUT`/anything else → 502), and never lets a raw
provider detail (a filesystem path, a library exception string) reach the client. If
post-processing is enabled and throws, the error is logged and the unpolished
IndicTrans2 output is returned rather than failing the whole request.

### backend/src/services/languageRegistry.js
The single source of truth for which languages this app's translator supports —
English plus Hindi, Tamil, Kannada, Telugu, and Malayalam, each keyed by a FLORES-200
code (`eng_Latn`, `hin_Deva`, etc.) with a display label and native-script string.
Exports `LANGUAGES`, `LANGUAGE_CODES`, `ENGLISH`, `AUTO` (the sentinel value a client
may send as `sourceLanguage`), `isKnownLanguage()`, and `isSupportedPair()` (both codes
known and not identical). Its own header comment documents that this must be kept in
sync by hand with `indictrans-service/app/languages.py`'s equivalent Python dict — every
other file (route, service, rate limiter, frontend panel) reads from one of these two
registries rather than hardcoding a language list, so adding a language is a
three-file change (this file, the Python equivalent, and the frontend's display array)
plus confirming the model checkpoint actually covers it.

### backend/src/services/languageDetect.js
Auto-detect for the translator's `"auto"` source option — deliberately **not** an LLM
call and not a general-purpose language-ID library. It exploits the fact that five of
the six supported languages each occupy a distinct, non-overlapping Unicode script
block (Devanagari/Tamil/Telugu/Kannada/Malayalam) and the sixth (English) is Latin
script, so `detectLanguage(text)` just counts which script's characters dominate the
input. If the winning script holds less than 60% of all recognized letters
(`MIN_CONFIDENCE`), it returns `{language: null}` rather than guessing — the route then
asks the user to pick manually instead of risking a wrong-language translation.

### backend/src/services/glossary.js
A minimal terminology-substitution pre-processing step, applied only when translating
*from* English: known technical terms (currently just two example entries, `bearing`
and `shaft`, each mapped to a pre-approved Tamil rendering) are swapped for their
approved target-language form before the text reaches IndicTrans2, using a
word-boundary-safe regex so "bearing" doesn't also match inside "bearings" or
"forbearing". Its own comments frame this explicitly as a proof-of-mechanism, not a
real terminology database — growing it into a file/DB-backed glossary supporting
Indic-keyed lookups too is documented as deliberately deferred future work.

### backend/src/services/translationPostProcess.js
The optional, off-by-default Qwen3 fluency-polish pass. `postProcessTranslation({text,
targetLanguage})` sends IndicTrans2's raw output to the local Ollama `/api/chat`
endpoint with a system prompt explicitly forbidding re-translation or any response to
the text's content — "only fix obvious grammar/fluency issues... output ONLY the
corrected text." It's a standalone direct-fetch implementation rather than a reuse of
either `backend/src/llm/ollamaClient.js` (dead code, wrong config module — see below)
or `backend/src/services/ollamaService.js` (the live client, but built around streaming
chat rather than one polish call), to avoid quietly introducing a second source of
truth for the Ollama endpoint. Any failure here throws and is caught by
`translationService.js`, which falls back to the unpolished output.

### backend/src/routes/translate.test.js
Route-level test coverage for `/api/translate`: auth/rate-limit gating, request-body
validation (bad language codes, missing/oversized text), the same-language short-circuit
(source equals target, and auto-detect resolving to the target), correct mapping from
`TranslationError` variants to their HTTP status codes, and that a translation failure's
raw provider detail never leaks into the client-facing error body or the safe log line.

### backend/src/routes/translatePostProcess.test.js
Focused tests for the post-processing integration specifically: confirms
`TRANSLATION_POST_PROCESSING=false` (the default) never calls Ollama at all, that
enabling it does call it and returns the polished text, and — the important safety
property — that a post-processing failure (Ollama down, bad response) still returns
the original unpolished IndicTrans2 translation with a 200, rather than turning an
already-successful translation into a client-visible error.

### indictrans-service/app/config.py
Env-driven settings for the Python service, read once at import time, mirroring the
Node backend's `config.js` convention. Key values: `host`/`port` (used only for
self-reported `/health` info and logging — actual binding is controlled by how
`uvicorn` is invoked), `model_path` (base directory containing the three downloaded
checkpoint subfolders, with no hardcoded default — an unset path is treated as a real
setup error), `device` (`auto`/`cpu`/`cuda`), and generation limits (`max_input_chars`,
`max_new_tokens`, `num_beams`) deliberately kept modest for a CPU-fallback desktop
case.

### indictrans-service/app/languages.py
The Python mirror of `languageRegistry.js`: the same six FLORES-200 codes and labels,
plus `resolve_direction(source_lang, target_lang)` — the actual "translation router."
It returns one of three `ModelDirection` constants (`en-indic`, `indic-en`,
`indic-indic`) based on which side (if either) is English, or `None` for an unknown or
same-language pair. This function is the single place that decides which of the three
separately-loaded checkpoints handles a given request.

### indictrans-service/app/main.py
The FastAPI app itself. A `lifespan` startup hook calls `registry.load_all()` once
before accepting traffic. `GET /health` reports `"ok"` as soon as *any* one of the
three directions has loaded (not all three — a user may legitimately have only
downloaded one or two checkpoints). `POST /translate` enforces the character limit,
calls `resolve_direction()`, and on success returns `{translation}`; on failure it maps
`ModelNotLoadedError`/`EmptyOutputError`/anything else to a structured `{error_code,
detail}` JSON body via the shared `_error()` helper, explicitly never leaking a raw
exception (which could contain a filesystem path from a torch/transformers internal
error) to the caller — logged in full server-side instead. This service is documented
as loopback-only by convention and performs no authentication of its own, since its only
expected caller is the already-authenticated Node backend on the same machine.

### indictrans-service/app/model_registry.py
Loads and caches IndicTrans2's three directional checkpoints exactly once at startup —
never per-request. `ModelRegistry.load_all()` resolves the actual device (`auto` probes
`torch.cuda.is_available()`), then for each of the three directions checks whether its
checkpoint directory exists and, if so, loads it via `_load_one()`: a standard
HuggingFace `AutoTokenizer`/`AutoModelForSeq2SeqLM` (`trust_remote_code=True`, since
IndicTrans2 ships a custom modeling class) plus an `IndicProcessor` from the
`IndicTransToolkit` package, which performs the script-aware pre/post-processing
IndicTrans2's own usage pattern requires. A missing or broken checkpoint for one
direction is logged and left `None` — that direction then returns
`MODEL_NOT_LOADED`/503 for requests needing it — rather than crashing the whole service
or the other two directions, since a user may legitimately have downloaded only some
of the three. The module-level `translate(direction, source_lang, target_lang, text)`
function runs the actual inference for one request: preprocess via `IndicProcessor`,
tokenize, `model.generate()` with beam search, decode, postprocess, and raise
`EmptyOutputError` if the result is blank.

### indictrans-service/app/schemas.py
Pydantic request/response models forming the fixed Node↔Python contract: `TranslateRequest`
(`source_lang`, `target_lang`, `text`), `TranslateResponse` (`translation`),
`ErrorResponse` (`error_code` — a `Literal` of the four known codes Node's
`translationService.js` switches on — plus an optional server-only `detail`), and
`HealthResponse` (`status`, `models_loaded` per-direction, `device`). The file's own
comment flags these field names as a breaking-change boundary: `translationService.js`
parses this shape directly, so renaming a field here requires a matching Node-side
change.

### indictrans-service/scripts/download_model.py
Not read in this pass in full detail, but referenced throughout the docs as the
one-time, explicit download step (`python scripts/download_model.py --dest ./models`)
that pulls the three HuggingFace checkpoints (`ai4bharat/indictrans2-en-indic-dist-200M`,
`indictrans2-indic-en-dist-200M`, `indictrans2-indic-indic-dist-320M`) into the
directory structure `model_registry.py` expects — the Node backend never downloads or
auto-starts this service or its models.

### frontend/src/translator/TranslatorPanel.jsx
The Translator tab's UI: language-pair pickers (From, defaulting to Auto Detect / To),
a text area with a live character counter against the same `TRANSLATE_MAX_CHARS`
limit the backend enforces, a Translate button (also bound to Ctrl+Enter), and a Swap
button disabled whenever "Auto Detect" is selected (there's nothing concrete to swap
with). It calls the `translate` group in `services/api.js` (`POST /translate`, with a
200-second client timeout matching the backend's generous IndicTrans2 timeout), shows
the returned translation, and surfaces the route's safe error message directly
(service unavailable, timeout, unsupported pair, rate-limited) rather than a generic
failure string. Its `LANGUAGES` display array (label + native script per code) is the
third place — alongside the two backend registries — that needs a new entry when
adding a supported language.

## Frontend: build/packaging pipeline

### frontend/electron/main.js
The Electron main-process entry point. Uses `app.requestSingleInstanceLock()` so a
second launch attempt hands off to the already-running instance instead of racing two
processes over the same backend port; `app.whenReady()` then installs a permission
handler restricting microphone/camera access to the app's own `file://` page, registers
every `ipc/*.js` handler module, calls `BackendManager.ensurePortFree(BACKEND_PORT)`
followed by `BackendManager.startBackend(app)`, waits (with a 15s timeout, non-fatal on
failure) for the backend's health endpoint via `BackendHealth.waitForBackend()`, then
creates the main window and starts the wake-word detector, clipboard poller, and global
shortcut. Its own comments explain the single-instance lock and `ensurePortFree` call
together close a real bug: without them, a killed/crashed previous launch could leave
an orphaned backend — potentially running old pre-migration code against the old
JSON-file "database" instead of real SQLite — silently serving every future launch
indefinitely.

### frontend/electron/managers/BackendManager.js
Owns spawning and reclaiming the Node backend as a child process. `ensurePortFree(port)`
(Windows-only; a no-op elsewhere) shells out to `netstat -ano -p tcp`, finds any PID
listening on the target port that isn't this process, and force-kills it via
`taskkill /PID <pid> /F` — since the single-instance lock guarantees this process is
the sole legitimate owner by the time it runs, anything already there is by definition
a stale leftover, never a peer to coordinate with. `startBackend(app)` resolves the
backend's `server.js` path via `pathHelper.js`, spawns it using Electron's own binary
with `ELECTRON_RUN_AS_NODE=1` (so no separate Node install is required) and a
`NODE_PATH` pointed at the packaged `resources/backend/node_modules` (or, in dev, the
frontend's own `node_modules` plus the sibling backend directory), and appends (never
truncates) stdout/stderr to a persistent `backend.log` under Electron's userData path
so a crash from a previous session stays diagnosable after a restart. `killBackend()`
terminates the tracked child process on app shutdown.

### frontend/scripts/prepare-backend.cjs
A pre-packaging build step. Because the repo uses npm workspaces, `backend/node_modules`
is hoisted (and incomplete) at the root, so a naive package would ship a backend
missing dependencies like `express`. This script does an isolated `npm install
--omit=dev` in a scratch temp directory (outside the workspace, so nothing hoists),
then assembles `frontend/backend-runtime/` from the backend's `src/`, `scripts/`,
`package.json`, and that scratch install's complete `node_modules` — the self-contained
bundle `electron-builder` then copies into the packaged app's resources.

### frontend/scripts/afterPack.cjs
An `electron-builder` `afterPack` hook, since `electron-builder`'s own `extraResources`
mechanism silently skips `node_modules` directories. It copies the
`backend-runtime/` bundle `prepare-backend.cjs` assembled into
`<packed-app>/resources/backend`, so the shipped `.exe`'s installer actually contains a
runnable backend with all its dependencies.

**Note on the Python translation service and packaging:** the IndicTrans2 microservice
is explicitly *not* part of this packaging pipeline. `docs/translation-architecture.md`
documents it as a deferred future phase — no Python runtime bundling, no
auto-start/stop lifecycle from the Electron main process. In the packaged `.exe`, chat/
RAG/documents work immediately; the Translator tab requires the user to separately
`uvicorn app.main:app` the Python service (and have Ollama running) alongside the app,
or it returns a clear 503 rather than crashing.

## A note on intent classification and the translator

`backend/src/ai/IntentClassifier.js` is covered in detail in the AI/Agent-system
section below — it exists, but it classifies a chat message into one of **seven Windows
repair domains** (`automation`, `bluetooth`, `network`, `performance`, `file`,
`security`, `windows`) for the separate autonomous repair-agent pipeline
(`ai/Orchestrator.js`). It has no translation domain and is never invoked by
`routes/translate.js` or `translationService.js`. There is currently no code path that
infers "the user wants a translation" from a chat message and routes it to
`translateText()` — the Translator is reached only by the dedicated sidebar tab or a
direct `POST /api/translate` call.

## Backend: AI / Repair-Agent System

This codebase actually contains two complete, independently-wired repair pipelines, not one legacy and one live. The older `agent/` (singular) module — `agentBrain.js`, `agentLoop.js`, `dangerClassifier.js`, `powershellRunner.js` — is mounted directly by `routes/agent.js` (which imports `runAgent` from `agentLoop.js`) and drives a single general-purpose ReAct loop with no domain routing. The newer `ai/` + `agents/` (plural) system is mounted by `routes/repair.js` (which imports `runRepair` from `ai/Orchestrator.js`) and adds intent classification, planning, and domain-specialized agents on top — but critically, `agents/BaseAgent.js` (the base class for every domain agent) imports its core primitives — `decideNextStep`, `AGENT_DEFAULT_MODEL`, `classifyCommand`, `runPowerShell` — directly from the `agent/` folder, so the "legacy" module is in fact the shared execution engine underneath both pipelines. `agentLoop.js` itself, however, is only used by the simple `/api/agent` route; the enterprise `/api/repair` route reimplements the same loop logic inside `BaseAgent.run()`.

### backend/src/agent/agentBrain.js
This is the reasoning core shared by both pipelines: it prompts a local Ollama model with a strict JSON ReAct contract (`thought`/`command`/`done`/`answer`) so the model proposes exactly one PowerShell command per turn based on the goal and prior step transcript. Its main export is `decideNextStep({goal, steps, model, systemPrompt, signal})`, which posts to Ollama's `/api/generate` with `format: "json"`, parses (or salvages) the JSON response, and returns a normalized decision object; it also exports `AGENT_DEFAULT_MODEL` (from `AGENT_MODEL` env, default `qwen3`) and the default `SYSTEM_PROMPT` used by the simple agent. It depends only on `../config.js` for the Ollama URL/keep-alive, and is imported by `agent/agentLoop.js`, `agent/runAgent.cli.js`, and `agents/BaseAgent.js` (which supplies its own domain-specific system prompt instead of the default one).

### backend/src/agent/agentLoop.js
Orchestrates the diagnose-act-observe loop for the simple, non-domain-routed agent: it repeatedly calls `decideNextStep`, classifies the proposed command's risk with `classifyCommand`, executes it via `runPowerShell` unless it is blocked, and feeds the result back in, streaming every step through an `onEvent` callback until the model signals `done` or `maxSteps` is hit. Its sole export, `runAgent({goal, model, maxSteps, signal, onEvent})`, returns a final `{answer, steps, stopped}` summary and asks the brain for a closing recommendation if the step limit is reached first. It imports `decideNextStep`/`AGENT_DEFAULT_MODEL` from `agentBrain.js`, `classifyCommand` from `dangerClassifier.js`, and `runPowerShell` from `powershellRunner.js`, and is consumed by `routes/agent.js` (the live `/api/agent` HTTP route) and `agent/runAgent.cli.js`.

### backend/src/agent/dangerClassifier.js
Classifies any PowerShell command string into `read` (always safe), `fix` (mutating but recoverable, auto-run), or `blocked` (irreversible/disruptive, never auto-run), using two pattern lists: `BLOCKED_PATTERNS` (disk formatting/partitioning, recursive deletion of system paths, registry hive wipes, account creation/deletion, disabling Defender or the firewall, execution-policy weakening, download-and-execute one-liners, service deletion, registry autostart persistence, reboot/shutdown, and killing critical processes) and `READ_ALLOWLIST` (verbs like `Get-`, `Test-`, `ipconfig`, etc.). Its exported `classifyCommand(command)` splits the input on `|`, `;`, newlines, `&&`/`||` so every statement in a chained command is checked individually — a command is only `read` if every segment matches the allowlist. This is the single shared security gate: it's called directly by `agent/agentLoop.js` and, identically, by `agents/BaseAgent.js`, meaning every command from both the simple agent and all seven domain agents passes through this one function before any PowerShell process is spawned.

### backend/src/agent/dangerClassifier.test.js
A `node:test` suite that locks in the risk classifications produced by `dangerClassifier.js`, covering both the categories added in a later security-audit "phase" (account/privilege escalation, disabling Defender, disabling the firewall wholesale, execution-policy weakening, download-and-execute one-liners, service deletion, raw-text registry autostart writes) and the earlier baseline blocked categories (disk formatting, `diskpart`, recursive deletion of `C:\Windows`, local user removal, forced reboot, killing `lsass`). It also asserts that legitimate read-only diagnostics and recoverable fixes (`Get-Process`, `ipconfig /flushdns`, `Restart-NetAdapter`, `Start-Service`) are not misclassified as blocked. It imports only `classifyCommand` from `./dangerClassifier.js` and exists purely as a regression test, not something imported elsewhere.

### backend/src/agent/powershellRunner.js
A self-contained (no Electron dependency), headless PowerShell executor usable from either the API server process or a CLI harness. Its export `runPowerShell(command, {timeout})` spawns `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -Command <command>` via Node's `child_process.spawn`, captures stdout/stderr, truncates output beyond 6,000 characters, enforces a 60-second default timeout (SIGTERM then SIGKILL), and resolves with `{stdout, stderr, exitCode, timedOut}`. It has no internal dependencies beyond `node:child_process`, and is imported by both `agent/agentLoop.js` and `agents/BaseAgent.js`, making it the single point where every agent (simple or domain-specialized) actually touches the Windows shell.

### backend/src/agent/runAgent.cli.js
A standalone CLI test harness for exercising the simple agent loop end-to-end outside of Electron or the HTTP server, invoked as `node src/agent/runAgent.cli.js "<problem>" [--model x] [--max n]`. It parses command-line arguments into a goal/model/maxSteps, then calls `runAgent()` with an `onEvent` handler that pretty-prints thoughts, commands, blocked warnings, command output, and the final answer to the terminal with ANSI colors. It imports `runAgent` from `./agentLoop.js` and `AGENT_DEFAULT_MODEL` from `./agentBrain.js`, and is a leaf script — nothing else imports it.

### backend/src/agents/AgentRegistry.js
A small lookup table mapping domain names to singleton instances of each specialized repair agent, used to route a classified problem to the right agent. Its exports are `getAgent(domain)`, which returns the matching instance from the internal `registry` object or falls back to `registry.windows` (the general-purpose `WindowsRepairAgent`) for any unrecognized domain, and the `registry` object itself. It imports all seven agent classes (`BluetoothAgent`, `NetworkAgent`, `PerformanceAgent`, `FileRepairAgent`, `SecurityAgent`, `WindowsRepairAgent`, `AutomationAgent`) and is imported by `ai/Orchestrator.js`, which is the only consumer.

### backend/src/agents/AutomationAgent.js
A thin `BaseAgent` subclass declaring the identity for the automation domain: scheduled backups, file sync, timed scripts, logon apps, cleanup jobs, and periodic diagnostics via Windows Task Scheduler. Its constructor supplies `domain: 'automation'`, a `title`, and an `expertise` string instructing the model to check for existing tasks before creating new ones, prefer disabling over deleting, prefix task names with "Chanakya-", and explicitly ask about missing details (retention, sync direction) rather than guessing for destructive recurring jobs. It has no behavior of its own beyond `BaseAgent`, importing only `./BaseAgent.js`, and is instantiated once in `agents/AgentRegistry.js`.

### backend/src/agents/BaseAgent.js
The shared engine for every specialized domain agent, implementing the same think-run-observe ReAct loop as `agent/agentLoop.js` but parameterized per-domain. Its exported `BaseAgent` class takes `{domain, title, expertise}` in its constructor, exposes `buildSystemPrompt(knowledge, plan)` (which assembles the agent's identity, a fixed `REACT_CONTRACT` describing the JSON decision format, the domain's repair-guide knowledge, and the planner's suggested steps into one system prompt), and `run({goal, knowledge, plan, model, maxSteps, signal, onEvent})`, which loops calling `decideNextStep`, gating each proposed command through `classifyCommand`, executing non-blocked commands with `runPowerShell`, and emitting `thought`/`command`/`blocked`/`output`/`error`/`aborted` events. It imports `decideNextStep`/`AGENT_DEFAULT_MODEL` from `../agent/agentBrain.js`, `classifyCommand` from `../agent/dangerClassifier.js`, and `runPowerShell` from `../agent/powershellRunner.js`, and is extended by all seven files in `agents/` (BluetoothAgent, NetworkAgent, PerformanceAgent, FileRepairAgent, SecurityAgent, WindowsRepairAgent, AutomationAgent), each invoked in turn by `ai/Orchestrator.js`.

### backend/src/agents/BluetoothAgent.js
A minimal `BaseAgent` subclass for the bluetooth domain, whose constructor sets `domain: 'bluetooth'`, `title: 'Bluetooth Agent'`, and an `expertise` string focused on Bluetooth radios, the `bthserv` service, pairing, and wireless audio, noting the distinction between a disabled adapter and a software radio switch. It adds no methods of its own — all execution logic is inherited from `BaseAgent`. It imports only `./BaseAgent.js` and is instantiated in `agents/AgentRegistry.js`, reached whenever `ai/IntentClassifier.js` classifies a problem as `bluetooth`.

### backend/src/agents/FileRepairAgent.js
A minimal `BaseAgent` subclass for the file domain, with `domain: 'file'`, `title: 'File Repair Agent'`, and an `expertise` string covering missing/hidden files, permissions, ownership, Explorer issues, and filesystem corruption, explicitly instructed to recommend rather than automatically delete or overwrite user data. It has no additional logic beyond the inherited `BaseAgent.run()`. It imports only `./BaseAgent.js` and is instantiated in `agents/AgentRegistry.js` for problems classified as `file`.

### backend/src/agents/NetworkAgent.js
A minimal `BaseAgent` subclass for the network domain, with `domain: 'network'`, `title: 'Network Agent'`, and an `expertise` string covering Wi-Fi/Ethernet adapters, IP configuration, DNS, DHCP, and gateways, instructed to prefer least-disruptive fixes (flush DNS, renew IP) before resetting adapters or the TCP/IP stack. It adds no behavior beyond `BaseAgent`. It imports only `./BaseAgent.js` and is instantiated in `agents/AgentRegistry.js`.

### backend/src/agents/PerformanceAgent.js
A minimal `BaseAgent` subclass for the performance domain, with `domain: 'performance'`, `title: 'Performance Agent'`, and an `expertise` string covering slowness, freezing, high CPU/RAM/disk usage, low disk space, and startup bloat, instructed to identify the exact offending process before acting and never kill critical system processes. It has no logic beyond the inherited loop. It imports only `./BaseAgent.js` and is instantiated in `agents/AgentRegistry.js`.

### backend/src/agents/SecurityAgent.js
A minimal `BaseAgent` subclass for the security domain, with `domain: 'security'`, `title: 'Security Agent'`, and an `expertise` string covering Windows Defender, firewall, malware detection, and threat remediation, explicitly restricted to only enabling/strengthening protection and running scans, never disabling security as a "fix." It adds no additional logic. It imports only `./BaseAgent.js` and is instantiated in `agents/AgentRegistry.js`.

### backend/src/agents/WindowsRepairAgent.js
A minimal `BaseAgent` subclass acting as the catch-all fallback agent, with `domain: 'windows'`, `title: 'Windows Repair Agent'`, and an `expertise` string covering anything not owned by the other domains — audio, display, printers, drivers, services, Windows Update, and system-file integrity — instructed to check the event log and service/device state before making changes. It has no logic of its own beyond `BaseAgent`. It imports only `./BaseAgent.js` and is both registered under the `windows` key and returned by `AgentRegistry.getAgent()` as the default for any unrecognized domain.

### backend/src/ai/IntentClassifier.js
Decides which of seven domains (`automation`, `bluetooth`, `network`, `performance`, `file`, `security`, `windows`) a user's problem belongs to, using a fast regex keyword pass first and falling back to an LLM call for ambiguous inputs. Its export `classifyIntent(goal, {model, signal})` checks `goal` against per-domain regex arrays in `KEYWORDS` (with `automation` checked first so scheduling intent wins over topic keywords), and if nothing matches, calls `completeJSON` with a system prompt describing each domain, returning `{domain, confidence, reason, via}`; it degrades to the `windows` domain if Ollama is unreachable. It imports `completeJSON`/`DEFAULT_MODEL` from `./llmClient.js` and is imported by `ai/Orchestrator.js` as the first stage of the enterprise repair pipeline.

### backend/src/ai/Orchestrator.js
The top-level driver of the enterprise multi-agent repair pipeline, tying together intent classification, knowledge retrieval, planning, agent execution, and outcome analysis into one flow that streams typed events for the UI. Its export `runRepair({goal, model, maxSteps, signal, userId, onEvent})` calls `classifyIntent` to pick a domain, `loadGuide` to fetch that domain's RAG knowledge text, `createPlan` to produce a short ordered plan, `getAgent(domain).run(...)` to execute the diagnose/fix loop, `analyzeOutcome` to verify whether the problem was actually resolved, and finally `logSession` to persist the whole transcript for future training; it returns `{sessionId, domain, resolved, summary, recommendation}`. It imports from `./IntentClassifier.js`, `./Planner.js`, `./ResultAnalyzer.js`, `../knowledge/index.js`, `../agents/AgentRegistry.js`, `./llmClient.js`, and `./RepairLogger.js`, and is itself imported by `routes/repair.js` (the live `/api/repair` HTTP route) and `ai/runRepair.cli.js`.

### backend/src/ai/Planner.js
Produces a short (2-5 step), advisory diagnostic/repair plan for a problem, grounded in the domain's repair guide, that steers but does not constrain the downstream agent. Its export `createPlan({goal, domain, knowledge, model, signal})` calls `completeJSON` with a system prompt instructing a senior-engineer persona to diagnose before fixing, parses the returned `{steps, summary}` JSON, caps steps at six, and falls back to an empty plan with a generic summary if the LLM call fails. It imports `completeJSON`/`DEFAULT_MODEL` from `./llmClient.js` and is called by `ai/Orchestrator.js` as pipeline stage three, with its output passed into the chosen domain agent's `run()`.

### backend/src/ai/RepairLogger.js
Persists every completed repair and automation session (goal, domain, plan, executed steps, resolution verdict, and later user feedback) to disk for later fine-tuning, splitting them into separate JSON files (`repair-sessions.json` vs `automation-sessions.json` under `storage/training-data/`) so the two datasets can be cleaned/balanced independently, while also reading a legacy path if the new one is missing. Key exports include `logSession(session)` (writes a new record and returns its id), `addFeedback(id, worked, note, requesterUserId)` (attaches user feedback with an ownership check so only the recording user's account can rate their own session), `getSessions()` (a merged, newest-first read across both logs for the API), `exportTrainingData()`/`exportTrainingDataSplit()` (filter sessions through `isGoodSession` — which now deliberately keeps honest dead-ends and refused/blocked actions, not just successes — and render them via `buildExample` into chat-format `{messages: [...]}` training examples). It imports `../config.js` and `../knowledge/subdomains.js`, and is imported by `ai/Orchestrator.js` (to log sessions), `ai/exportDataset.cli.js`, and presumably `routes/repair.js` for the sessions/feedback/dataset endpoints.

### backend/src/ai/ResultAnalyzer.js
Acts as an automated QA reviewer that inspects the full transcript of an agent's commands and outputs and decides whether the user's original problem was actually resolved, rather than trusting the agent's own closing claim. Its export `analyzeOutcome({goal, steps, agentAnswer, model, signal})` renders the step transcript (including blocked steps) into text, calls `completeJSON` with a QA-reviewer system prompt asking for `{resolved, summary, recommendation}`, and falls back to an unresolved verdict with a generic recommendation if the LLM call fails. It imports `completeJSON`/`DEFAULT_MODEL` from `./llmClient.js` and is called by `ai/Orchestrator.js` as the final analysis stage before session logging.

### backend/src/ai/exportDataset.cli.js
A CLI script that exports the currently "good" logged repair/automation sessions as a fine-tuning-ready JSONL dataset, run as `node src/ai/exportDataset.cli.js [outPath]`. It calls `exportTrainingData()` and `getSessions()` from `RepairLogger.js`, writes each example as one JSON line to `storage/training-data/repair-dataset.jsonl` (or a given path), and prints a summary plus next-step guidance for LoRA fine-tuning a Qwen2.5 model and loading it back into Ollama. It imports `exportTrainingData`, `getSessions`, and `DATASET_DIR` from `./RepairLogger.js` and is a standalone leaf script with no other importers.

### backend/src/ai/llmClient.js
A thin, dependency-light wrapper around the local Ollama server used for structured JSON completions by the planning/classification layer of the enterprise pipeline. Its export `completeJSON({system, prompt, model, temperature, signal})` posts to `${config.ollamaUrl}/api/generate` with `format: "json"` and `stream: false`, then parses the response text as JSON (salvaging the first `{...}` block if the model wrapped it in prose), throwing descriptive errors for unreachable Ollama or missing models; it also exports `DEFAULT_MODEL` (from `AGENT_MODEL` env, default `qwen3`). It imports only `../config.js` and is used by `ai/IntentClassifier.js`, `ai/Planner.js`, and `ai/ResultAnalyzer.js` — essentially every LLM call in the enterprise pipeline outside of the agent's own ReAct step, which instead uses `agent/agentBrain.js`'s near-identical but separate implementation.

### backend/src/ai/runRepair.cli.js
A standalone CLI harness for the enterprise multi-agent repair pipeline, invoked as `node src/ai/runRepair.cli.js "<problem>" [--model x] [--max n]`. It parses arguments, calls `runRepair()` from `Orchestrator.js` with an `onEvent` handler that prints color-coded output for each pipeline stage — intent classification, plan, agent handoff, thoughts, commands, blocked warnings, command output, and the final resolved/unresolved verdict with recommendation. It imports `runRepair` from `./Orchestrator.js` and `DEFAULT_MODEL` from `./llmClient.js`, and is a leaf script with no other importers, serving as the enterprise-pipeline counterpart to `agent/runAgent.cli.js`.
## Backend: Routes & Middleware

Every backend request enters through `backend/src/app.js`, which builds a single Express `app`: a correlation-id stamper, a helmet security-headers layer tuned for the packaged Electron renderer, a CORS allowlist restricted to `localhost`/`127.0.0.1`/`file://` origins, and the JSON body parser, all run before any router. `app.js` then mounts one Express `Router` per feature area at its own `/api/*` prefix (`/api/auth`, `/api/upload`, `/api/chat`, `/api/models`, `/api/history`, `/api/transcribe`, `/api/documents`, `/api/memory`, `/api/stats`, `/api/agent`, `/api/repair`, `/api/translate`), and each router applies its own middleware chain on top of that shared baseline — typically `requireAuth` (session verification), sometimes `requireAdmin` (role check), and for the AI-heavy endpoints (chat/agent/repair/transcribe/upload) the shared `askLimiter` rate limiter. Any request that reaches app.js's own catch-all handlers falls through to a JSON 404 for unmatched `/api` routes or a generic error handler that echoes deliberately-thrown 4xx messages but hides anything else behind a generic "Unexpected local server error." Two files reviewed here — `ask.js` and `ingestRoute.js` — export routers that are not referenced anywhere in `app.js`; they read as an earlier prototype RAG pipeline (SQLite `usage_log`, LanceDB-style ingest) sitting alongside, but disconnected from, the router set the app actually serves.

### backend/src/routes/agent.js
Registers `POST /` (mounted as `/api/agent`) behind `requireAuth` and the shared `askLimiter`. It validates a required `goal` string (non-empty, ≤4000 chars) and an optional `maxSteps` bounded to 1–50 via `boundedInt`, then streams an NDJSON response (`thought | command | output | blocked | final | error | aborted` events) by calling `runAgent()` from `agent/agentLoop.js`, forwarding the request's abort `signal` so a dropped client connection cancels the run. The route exists to drive autonomous, unattended PowerShell troubleshooting sessions, and a comment notes it now requires auth specifically because this and `/api/repair` previously ran with no authentication check at all.

### backend/src/routes/apiSecurity.test.js
A broad HTTP-level security regression suite run against the live `app` (in-process `http.createServer`) covering security headers, the JSON 404 fallback, unsupported HTTP methods, content-type/malformed-JSON handling, CORS origin allow/deny, oversized-input rejection across memory/history/chat/agent bodies, invalid resource-id (non-UUID) rejection, HTTP parameter pollution, prototype-pollution safety on `PATCH /auth/profile`, search-result pagination caps, and file-upload security (bad magic-byte signatures, unsupported extensions, path-traversal filenames), plus a check that error responses never leak stack traces, filesystem paths, or raw DB errors.

### backend/src/routes/ask.js
A standalone RAG chat endpoint, `POST /ask`, built on a different config/DB module (`config/index.js`, `db/connection.js`) than the rest of the app and not imported by `app.js`, so it is effectively dead code. It embeds the question, runs `vectorSearch`/`rerank`/`compressContext`, builds a prompt via `promptBuilder.js`, streams the model's answer over SSE using `chatCompletionStream`, logs token usage to a `usage_log` SQL table, and finally emits a `done` SSE event with usage stats and cited sources.

### backend/src/routes/auth.js
Defines the full authentication surface at `/api/auth`: `POST /register` and `POST /login` (each behind `ipAuthLimiter` plus their own dedicated limiter, and login additionally behind `progressiveLoginDelay`), `POST /logout` and `GET /me` (behind `requireAuth`), `POST /change-password` and `DELETE /account` (behind `requireAuth`, re-verifying the current password), `POST /forgot-password` and `POST /reset-password` (behind `ipAuthLimiter` plus their own limiters, both returning identical responses regardless of account existence to prevent enumeration), and `PATCH /profile` (behind `requireAuth`). All routes delegate the real logic to `services/authService.js` and `services/sessionService.js`; a shared `respondToAuthError` helper only echoes an error's message back to the client when it is a deliberately-thrown `AuthError`, otherwise logging it and returning a generic 500. `PATCH /profile` deliberately never reads `role` (or other privileged fields) from the request body, closing a mass-assignment/privilege-escalation path.

### backend/src/routes/authErrorHandling.test.js
Confirms the auth routes' error-handling contract: a deliberate validation failure (e.g. a too-short password) still returns its specific message with 400, while a genuine unexpected failure — simulated by forcibly closing the shared `db` connection — returns a generic "Unexpected local server error." with 500 and never leaks the word "database" or any internal detail, for both `/register` and `/login`.

### backend/src/routes/authIdentity.test.js
Locks in that authenticated identity comes exclusively from the verified Bearer session (`request.userId`), never from a spoofable `x-user-id` header or a `userId`/`ownerId` field in the request body/query — tested across `GET /auth/me`, memory creation/listing, chat, and combined "every spoofable field" attempts, plus confirming no `Authorization` header at all yields 401 even with a spoofed header present.

### backend/src/routes/authorization.test.js
A broad RBAC/IDOR-BOLA regression suite: verifies `PATCH /auth/profile` ignores `role`/`isAdmin`/`permissions` in the body (no privilege escalation), that `/repair/sessions` and `/repair/dataset` are 401 unauthenticated / 403 non-admin / 200 admin, that `POST /models/unload` now requires auth, and extensive per-user ownership isolation (memory, documents, history conversations/folders, repair-session feedback) proving one user can never read, rename, or delete another user's resources — cross-user deletes/renames resolve as silent no-ops rather than errors.

### backend/src/routes/authorizationRbac.test.js
A smaller follow-on suite covering two cases not already exercised elsewhere: that a caller cannot redirect a `PATCH /auth/profile` update onto another user's account via `id`/`userId`/`targetUserId`/`accountId` fields in the body, and one combined end-to-end scenario (document + memory + conversation) that asserts cross-user isolation by inspecting actual response data, not just HTTP status codes.

### backend/src/routes/chat.js
Registers `POST /` (mounted as `/api/chat`, behind `requireAuth` and, via `app.js`, `askLimiter`) as the main chat endpoint. It validates the model against `supportedModels`, bounds `message` (≤50,000 chars) and `history` (≤500 items) length, and validates `conversationId` shape. It builds a system prompt from RAG sources (`searchChunks`), optional screen-capture context, an `agentProfile` persona (coder/writer/analyst), and tool-use guidance when `tools` are supplied, then streams the model's reply as NDJSON via `streamChat()` from `services/ollamaService.js`, emitting `sources`, `token`, `tool_call`, and `done` events. It persists both the user's and the assistant's turns via `appendHistory()`, retries once without tools if the model rejects the `tools` parameter, and attaches base64 images to the final user message for vision input.

### backend/src/routes/documentPipeline.test.js
Exercises the upload pipeline's edge cases against the live app (no live Ollama, so embedding always fails, and tests assert on behavior true either way): that uploaded temp files are always removed from `config.uploadDir` regardless of outcome (success, validation failure, or delete), that a parser exception on one file in a batch no longer aborts the rest of the batch, that `chunkText`'s `MAX_CHUNKS` cap rejects oversized documents before any embedding is attempted, and that document content — including prompt-injection-styled text — is treated purely as inert data by both the upload route and `classifyCommand()`.

### backend/src/routes/documents.js
Mounted at `/api/documents` behind `requireAuth` for the whole router. `GET /` merges per-user document metadata from `documentsStore.getDocuments()` with indexed-vector metadata from `vectorService.listIndexedDocuments()` (indexed data as the base, store data overlaid) and returns `{ documents }`. `DELETE /:documentId` (behind `requireUuidParam`) calls `deleteDocument(documentId, userId)`, scoped to the caller so deleting another user's document id is a no-op, and returns `{ ok: true }`.

### backend/src/routes/history.js
Mounted at `/api/history` behind `requireAuth`. `GET /` returns `{ conversations, folders }` for the caller. `GET /search` validates and collapses a possibly-repeated `?q=` query param and calls `searchChats()`. `DELETE /:conversationId` and `PATCH /:conversationId` (both `requireUuidParam`-guarded) delete or update a conversation (rename, pin, bookmark, folder reassignment — carefully distinguishing an absent `folderId` from an explicit `null`), converting a service-level "Folder not found." error into a 400. `POST /folders`, `PATCH /folders/:folderId`, and `DELETE /folders/:folderId` manage folders, each scoped to `request.userId` so cross-user folder edits are no-ops or rejected.

### backend/src/routes/ingestRoute.js
Defines `POST /ingest/run`, a batch job that loads records from a separate source DB (`ingest/loadSources.js`) and embeds/stores them (`ingest/embedAndStore.js`), returning progress counters (`processed`, `nextOffset`, `inserted`, `skipped`, `done`). Like `ask.js`, this router is not imported by `app.js`, so it is not part of the live API surface — its own comment recommends running it as a CLI script or background job rather than synchronously from a request in production.

### backend/src/routes/memory.js
Mounted at `/api/memory` behind `requireAuth`. `GET /` lists memories for the caller, optionally filtered by a `type` enum (`session`/`pinned`/`project`) validated via `requireEnum` after collapsing a possibly-repeated query param. `POST /` validates `content` (≤8000 chars) and `type`, then calls `addMemory()` and returns 201. `DELETE /:memoryId` (`requireUuidParam`-guarded) and the bare `DELETE /` (clear-all, optionally type-filtered) both scope to `request.userId`, so they can never affect another user's memories.

### backend/src/routes/models.js
Mounted at `/api/models`. `GET /loaded` and `GET /` are deliberately left unauthenticated — they return only static/global Ollama model info fetched before login completes — while `POST /unload` requires `requireAuth` since it is a disruptive, mutating action that drops every loaded model from memory. `GET /` cross-references `supportedModels` from `config.js` against `listInstalledModels()` to report which configured models are actually installed, degrading gracefully (`connected: false`) if Ollama is unreachable.

### backend/src/routes/repair.js
Mounted at `/api/repair` behind `requireAuth` for the whole router (plus `askLimiter` applied in `app.js`). `POST /feedback` records whether a repair session "worked," validating `sessionId`/`worked`/`note`, and calls `addFeedback()` (from `ai/RepairLogger.js`), which enforces that a session with a recorded owner can only receive feedback from that owner (legacy, owner-less sessions accept feedback from anyone) — a mismatch returns 404. `GET /sessions` and `GET /dataset` are gated behind `requireAdmin` as they expose a shared cross-user training corpus. `POST /` streams the enterprise repair pipeline as NDJSON (`intent | plan | agent | thought | command | output | blocked | final | error | aborted` events) via `runRepair()` from `ai/Orchestrator.js`, with the same goal-length and `maxSteps` bounding as `agent.js`.

### backend/src/routes/resourceAbuse.test.js
Focuses on resource-exhaustion angles rather than repeating earlier validation tests: exhaustively checks every invalid `maxSteps` shape for `/api/agent` and `/api/repair`, confirms `/api/stats` now requires authentication, confirms `/api/transcribe` carries the same rate-limit headers as chat/agent/repair, confirms the legacy `/api/usage` route is gone (404), and sends a burst of 25 concurrent chat requests to prove the shared `askLimiter` actually throttles a burst (expects at least one 429) while the server stays responsive immediately afterward.

### backend/src/routes/stats.js
Mounted at `/api/stats` behind `requireAuth` for the whole router. `GET /` computes and returns live host metrics as JSON: CPU usage (derived by diffing `os.cpus()` samples across calls), RAM usage from `os.totalmem`/`os.freemem`, disk usage via `fs.statfs`, and the Node process's own heap usage — plus `gpu` and `temperature` fields that are explicitly mocked/randomized rather than measured.

### backend/src/routes/transcribe.js
Mounted at `/api/transcribe` behind `requireAuth` for the whole router, with `askLimiter` applied per-request since transcription is real CPU work. `POST /` accepts a single in-memory-uploaded `audio` file (≤15MB) via multer, writes it to a temp WAV file under `config.uploadDir`, calls `transcribeLocalWav()` from `services/speechService.js`, returns `{ text }`, and unconditionally removes the temp file in a `finally` block.

### backend/src/routes/upload.js
Mounted at `/api/upload`, `POST /` runs `requireAuth` → `askLimiter` → a multer disk-storage uploader (up to 500 files, `fileFilter` silently drops unsupported extensions) before the handler. For each accepted file it: rejects overlong filenames, extracts text via `extractDocument()` (skipping the file with a reason on `ValidationError` or parser exception rather than aborting the whole batch), chunks the text and rejects oversized documents against `MAX_CHUNKS`, embeds/indexes the chunks via `indexChunks()` (again skipping just that file on failure), and persists metadata per-document via `appendDocuments()` immediately after each successful index rather than batching at the end. Every file's temp copy on disk is removed in a `finally` block regardless of outcome. Responds 201 with `{ documents, skipped }`, where `skipped` entries carry a human-readable `reason`.

### backend/src/middleware/auth.js
Exports `requireAuth`, which reads a `Bearer <token>` from the `Authorization` header, verifies it via `sessionService.verifySession()`, and on success sets `request.userId`/`request.sessionToken` before calling `next()`; a missing or invalid/expired/revoked token returns 401. As a defense-in-depth checkpoint, it also validates that the session's `userId` is a well-formed UUID, since every downstream route and service trusts `request.userId` outright. It also exports `requireAdmin`, which must run after `requireAuth` and re-reads the caller's `role` directly from the `users` table (never trusting anything client-supplied) to gate admin-only routes, returning 403 for a non-admin.

### backend/src/middleware/auth.test.js
A large HTTP-level suite against the live app and its real middleware chain: valid/missing/malformed/wrong-scheme/tampered tokens all correctly 401; well-formed but unsigned/forged JWT-shaped tokens (including an `{"alg":"none"}` shape) are rejected outright, confirming the middleware does no JWT-style decode-and-trust; expired sessions, sessions for a deleted user (relying on an `ON DELETE CASCADE` foreign key rather than a per-request join), post-logout tokens, and post-password-reset tokens all correctly stop authenticating; error responses and server logs are checked to never leak the real token or a stack trace; and the forgot-password flow is confirmed to return an identical response for real vs. unknown usernames and for various malformed/oversized inputs.

### backend/src/middleware/errorHandler.js
A standalone Express error-handling middleware with the same contract as `app.js`'s own inline handler (echo a deliberately-thrown 4xx error's message, otherwise log server-side and return a generic 500) — noted in its own comment as not currently mounted anywhere, kept hardened in case it's wired in later.

### backend/src/middleware/rateLimiter.js
Defines every rate limiter used across the app, all built on `express-rate-limit`'s in-memory store (justified by the app being structurally single-instance, per an Electron single-instance lock). `askLimiter` is a flat 20-requests/minute ceiling shared by chat/agent/repair/transcribe/upload. The auth limiters are layered: `ipAuthLimiter` is a broad per-IP ceiling shared across register/login/forgot/reset; `loginLimiter` is keyed by `ip:username` and only counts failed attempts (`skipSuccessfulRequests`); `resetRequestLimiter` and `resetConfirmLimiter` similarly gate forgot-password and reset-confirm; `registerLimiter` is IP-only and only counts non-failure responses (`skipFailedRequests`) so typo-driven validation errors don't burn the account-creation budget. `translateLimiter` is keyed by `request.userId` rather than IP, since every request in this desktop app shares a loopback address. `progressiveLoginDelay` is a separate middleware that reads the counter `loginLimiter` already populated on `request.rateLimit` and adds an increasing `setTimeout` delay to login attempts past a threshold, before the hard 429 cutoff is reached.

### backend/src/middleware/rateLimiter.test.js
Deliberately-tight login-limiter tests (isolated in its own file/process to avoid cross-contaminating other limiters' budgets): confirms normal login/wrong-password behavior, that repeated failures against one account throttle to 429 after the configured max, that the 429 body is safe/generic, that the limit expires and login works again after the window rolls over, that a successful login doesn't consume the failure budget, that an unknown account throttles identically to a known one (no enumeration signal), that a spoofed `X-Forwarded-For` header cannot reset or bypass the limit, and that per-account throttling is independent across accounts.

### backend/src/middleware/rateLimiterForgot.test.js
Isolated tests for `resetRequestLimiter`: confirms repeated forgot-password requests throttle to 429 after the configured max and recover once the window expires, and that an unknown username is throttled identically to a known one.

### backend/src/middleware/rateLimiterIp.test.js
Isolated tests for `ipAuthLimiter`: confirms that cycling through many different usernames from one IP still gets throttled overall (closing the "rotate the username, not the IP" credential-stuffing gap), that the ceiling is shared across different auth endpoints (register/forgot/login) rather than tracked per-route, and that it expires after its window like the other limiters.

### backend/src/middleware/rateLimiterRegister.test.js
Isolated tests for `registerLimiter`: confirms normal registration works, excessive registration attempts throttle to 429 and recover after cooldown, and that failed/validation-error registration attempts do not consume the same budget that bounds real successful account creation (while genuine excessive successful volume is still throttled).

### backend/src/middleware/rateLimiterResetConfirm.test.js
Isolated test for `resetConfirmLimiter`: confirms repeated invalid-token reset-password attempts throttle to 429 after the configured max, with ordinary invalid-token 400s below that threshold.

### backend/src/middleware/translateRateLimit.test.js
Isolated tests for `translateLimiter`, stubbing out the IndicTrans2 translation service so requests that pass the limiter resolve quickly: confirms translation requests throttle to 429 per user after the configured max, that the budget is tracked per authenticated user rather than shared by IP (a second user from the same loopback address has an untouched budget), and that a rate-limited response never mentions the underlying provider (Ollama, model name, or loopback address).
## Backend: Services & Core Infrastructure

This slice of the codebase contains a real, wired-in application core alongside a substantial amount of dead scaffold code that only looks live at a glance. Two configuration modules exist — `backend/src/config.js` is the one actually imported everywhere the running app touches (`app.js`, `server.js`, every route, every live service); `backend/src/config/index.js` is a separate, never-imported-by-the-live-app config used only by an entirely dead subsystem. Likewise there are two "db" entry points, but they are not duplicates in the same sense: `backend/src/db/connection.js` owns the real SQLite connection and schema, and `backend/src/services/db.js` is simply a one-line wrapper that calls `getDb()` and re-exports it as `db` for the live services to use — both are live, just at different layers. The real dead weight is the entire `ingest/` and `retrieval/` RAG pipeline (`chunkText.js`, `cleanText.js`, `embedAndStore.js`, `loadSources.js`, `runIngest.js`, `compress.js`, `embedQuery.js`, `rerank.js`, `vectorSearch.js`) plus `llm/` (`ollamaClient.js`, `promptBuilder.js`, `tokenCount.js`): every one of these imports the dead `config/index.js`, several depend on a `chunks_vec` virtual table that `schema.sql` explicitly does not create (it needs the unbundled `sqlite-vec` SQLite extension), and grepping the codebase shows they're reachable only from unmounted routes (`routes/ask.js`, `routes/ingestRoute.js`) and a standalone `npm run ingest` CLI script — none of which `app.js` imports. The live document-upload/RAG path instead runs entirely through `lib/chunkText.js`, `services/ollamaService.js`, and `services/vectorService.js` (LanceDB), which is a separate, independently-written implementation of the same idea. `knowledge/index.js` and `knowledge/subdomains.js`, by contrast, are genuinely live — they're pulled into `ai/Orchestrator.js` and `ai/RepairLogger.js` to feed the repair-guide RAG context and training-data labels for the app's actual chat/repair-agent feature, unrelated to the dead ingest pipeline.

### backend/src/app.js
This is the live Express application: it builds the `app` singleton, stamps a `randomUUID()` request id on every request (echoed as `X-Request-Id` and used to correlate error logs), and applies `helmet` with a CSP tuned specifically to what the built React/Electron bundle actually needs (no inline scripts, `unsafe-inline` styles only because per-user accent colors are set via inline style attributes, `data:`/`blob:` allowed for pasted screenshots and OCR previews). Its CORS handler explicitly allows `origin === 'null'` because the packaged Electron renderer is a `file://` page, which browsers serialize as the literal string `"null"`, not `"file://..."` — a documented fix for a real bug where the naive `startsWith('file://')` check silently blocked the packaged app. It mounts every route module under `/api/*` (auth, upload, chat, models, history, transcribe, documents, memory, stats, agent, repair, translate), applies `askLimiter` to chat/agent/repair, serves the OCR language files and the built frontend as static assets with an SPA catch-all, and ends with a JSON 404 for unmatched `/api` paths and a generic error handler that only echoes `error.message` back to the client when the error was deliberately constructed with a 4xx `.status` (e.g. `ValidationError`), logging everything else server-side only.

### backend/src/appBoundary.test.js
A Node test-runner suite covering application-boundary security properties that aren't covered by other test files: it spins up `app.js` on a real `http.createServer` and asserts the actual OS-level bind address is `127.0.0.1` (not `0.0.0.0`), that an oversized JSON body is rejected with 413 before reaching any route, and that an unsupported HTTP method on a real path returns 404/405 rather than being silently accepted. It also spawns a fresh child Node process to prove `config.js` throws at module-load time when `OLLAMA_URL` is set to a non-loopback host (the SSRF guard), and separately scans the built `frontend/dist` bundle for secret-shaped strings (API-key patterns, PEM private keys, AWS key shapes) and for leftover `.map` source-map files, skipping gracefully if no build artifact is present.

### backend/src/server.js
The actual process entry point: it imports the live `app` and `config`, calls `getDb()` once at startup to initialize the SQLite database, then calls `app.listen(config.port, config.host, ...)` — binding explicitly to the configured host (loopback by default) rather than letting Node default to every interface. After listening, it fires a one-time, non-blocking, non-fatal health check against the separate IndicTrans2 translation microservice, logging whether it's reachable; a failure only logs a warning telling the operator to start the service, since the app is designed to fail per-request rather than at boot when an optional local AI backend isn't running.

### backend/src/config.js
This is the live, actually-imported configuration module for the whole application. On load it resolves an `ollamaUrl` and immediately throws if its hostname isn't loopback (`127.0.0.1`/`localhost`/`::1`), enforcing the app's stated design constraint that it never talks to a remote AI endpoint. It centralizes every runtime setting the real app uses: server host/port, model names, upload/vector/db/plugin/OCR storage paths derived from `APP_DATA_PATH`, the IndicTrans2 translation service URL and timeouts (with an optional, off-by-default Qwen3 post-processing pass), and a large `rateLimits` block tuning per-endpoint auth abuse protections (IP-wide, login, register, and reset limits, plus a progressive login delay). It also exports `supportedModels`, the list of Ollama models the UI lets a user pick from.

### backend/src/config/index.js
A second, structurally similar configuration module — but this one is not imported by anything the running server actually uses. It defines its own port default (3000 vs. the live config's 3001), its own model names (`chatModel`, `embedModel` under different env var names), a `dbPath` pointing at a nonexistent `./data/assistant.db`, and RAG-pipeline-specific tuning (`vectorTopK`, `rerankTopK`, `contextTokenBudget`, chunk sizing, per-model `contextLimits`). Every file that imports it belongs to the dead `ingest/`/`retrieval/`/`llm/` pipeline described in the section intro — this file is effectively that subsystem's private, unused config.

### backend/src/db/connection.js
The live SQLite connection module, imported by `server.js` and (via `services/db.js`) by every live service that touches the database. `getDb()` lazily constructs a single cached `better-sqlite3` `Database` instance pointed at `config.dbFile`, enables WAL journal mode and foreign-key enforcement, and executes `schema.sql` on every call to ensure the schema exists (all statements are `CREATE TABLE IF NOT EXISTS`, so this is safe to run repeatedly). This is the module that replaced an earlier hand-rolled JSON-file database shim.

### backend/src/db/schema.sql
Defines the real SQLite schema, including its own commentary explaining that it replaces a previous JSON-file-backed "database" whose regex-based SQL parser only ever honored the first clause of a compound `WHERE`, letting any caller who knew a resource id bypass ownership checks entirely. The live tables are `users`, `sessions` (only a token hash is stored), `password_resets` (same hash-only pattern, single-use via a non-null `usedAt`), `folders`, `chats`, `messages`, `memories`, and `documents`, most with a `userId` foreign key cascading on delete and an index on that column. A separate, explicitly-commented block at the bottom (`chunks`, `usage_log`) exists purely so the dead, unmounted ingest CLI and `routes/ask.js`/`routes/usage.js` don't hard-crash on a missing table; the schema deliberately does not create the `chunks_vec` virtual table that dead code's `vectorSearch.js` depends on, since it would require the unbundled `sqlite-vec` extension — real vector search in the live app is handled entirely by LanceDB via `services/vectorService.js`.

### backend/src/llm/ollamaClient.js
Part of the dead RAG pipeline: it imports the unused `config/index.js` and provides `embedText`, `chatCompletion`, and `chatCompletionStream` helpers that talk to Ollama's `/api/embeddings` and `/api/chat` endpoints directly. Nothing in the live application imports this file — the equivalent live functionality lives in `services/ollamaService.js`, which is structurally similar but independently written and reads from the live `config.js`.

### backend/src/llm/promptBuilder.js
Also part of the dead pipeline: `buildRagPrompt(question, contextChunks, history)` assembles a chat-messages array with a system prompt instructing the model to answer only from numbered, cited context chunks. It has no dependency on the dead config module itself, but it's only ever consumed by the unmounted `routes/ask.js`, so it never runs in the live server.

### backend/src/llm/tokenCount.js
Dead-pipeline utility: `estimateTokens` uses a ~4-characters-per-token heuristic, and `assertWithinContextLimit(model, promptText, maxCompletionTokens)` throws a 413-flagged error if a prompt plus reserved completion tokens would exceed a per-model limit pulled from the unused `config/index.js`'s `contextLimits` map. Not reachable from any live route.

### backend/src/retrieval/compress.js
Part of the dead retrieval pipeline: `pruneToRelevantSentences` scores a chunk's sentences by keyword overlap with the question and keeps only the top N (restoring original order afterward), `trimToTokenBudget` greedily keeps pre-ranked chunks until a token budget (from the dead config) is exhausted, and `compressContext` composes both steps. None of this is invoked by any live route.

### backend/src/retrieval/embedQuery.js
A one-line dead-pipeline wrapper: `embedQuery(question)` just calls `embedText` from the dead `llm/ollamaClient.js`. Unused by the live app.

### backend/src/retrieval/rerank.js
Dead-pipeline "poor man's rerank": combines vector similarity (`1 - distance`) with a keyword-overlap score at a 0.7/0.3 weighting to re-sort and truncate candidate chunks to `config.rerankTopK` (from the dead config module), with a comment noting it could be swapped for a real cross-encoder. Not used anywhere live.

### backend/src/retrieval/vectorSearch.js
Dead-pipeline vector search: `vectorSearch(queryEmbedding, topK, filter)` runs a raw SQL query against a `chunks_vec` virtual table joined to `chunks`, using SQLite's `MATCH`/`k =` vector-search syntax with an optional `source` filter. This table is never created by `schema.sql` (as that file's own comments state), so this function would throw if it were ever actually called from a live path — it is only reachable via the unmounted `routes/ask.js`.

### backend/src/ingest/chunkText.js
Dead-pipeline text chunker: splits text into sentence-boundary-respecting, token-sized (via the same 4-chars/token heuristic) overlapping chunks, sized from the dead `config/index.js`'s `chunkSizeTokens`/`chunkOverlapTokens`. Not the chunker actually used by document upload — that's `lib/chunkText.js`, a separate, differently-implemented (paragraph-first, with a hard `MAX_CHUNKS` cap) module wired into `routes/upload.js`.

### backend/src/ingest/cleanText.js
Dead-pipeline text normalizer: strips HTML tags, pagination boilerplate ("Page X of Y"), normalizes line endings, and collapses repeated whitespace/blank lines. Only consumed by `embedAndStore.js`, itself only reachable from the unmounted ingest CLI.

### backend/src/ingest/embedAndStore.js
Dead-pipeline record indexer: `embedAndStoreRecord(record)` cleans and chunks a source record's text, hashes each chunk with SHA-256 to skip re-indexing unchanged content, embeds new chunks via the dead `ollamaClient.embedText`, and inserts them into the `chunks`/`chunks_vec` tables via `db/connection.js`. Because `chunks_vec` doesn't exist in the real schema, the `insertVec` statement here would fail at runtime; this code only runs via the standalone `npm run ingest` script, never from the live server.

### backend/src/ingest/loadSources.js
An explicitly-labeled adapter-layer stub for pulling records from an external "source database" that this app doesn't actually have — it ships commented-out Postgres/MySQL examples and a placeholder `loadFromSourceDb`/`countSourceRows` implementation returning two hardcoded demo rows (a finance and an HR snippet). Purely scaffolding for the dead ingest CLI; there is no real source-database integration anywhere in this app.

### backend/src/ingest/runIngest.js
The CLI entry point for the dead ingest pipeline (`npm run ingest`), described in its own header comment as the "training step for RAG." It loops over `loadFromSourceDb` in batches of 200, calls `embedAndStoreRecord` per record, logs progress, and reports final counts — but since it depends on the demo placeholder source data and a `chunks_vec` table the real schema never creates, running it against the live database would not produce anything the running application uses.

### backend/src/knowledge/index.js
Live: this is the RAG-context loader for the app's actual repair-agent feature, imported by `ai/Orchestrator.js`. `loadGuide(domain)` reads and caches a markdown repair guide from `knowledge/repair-guides/<domain>.md`, returning an empty string if the file doesn't exist, and the Orchestrator injects the loaded guide as context for the domain-specialized agent it's about to run.

### backend/src/knowledge/subdomains.js
Live, used by `ai/RepairLogger.js`: defines the `SUBDOMAINS` map of fine-grained labels nested under each of the six canonical domains the app's `IntentClassifier` routes chat messages to (network, bluetooth, performance, file, security, windows), plus a seventh `automation` key that exists only for offline session-logging/training-data purposes and is never used for live intent routing. `isKnownSubdomain`, `normalizeSubdomain`, and `domainLabel` validate and format these labels (e.g. producing `"windows (audio)"`) for the training/logging prompts `RepairLogger` builds.

### backend/src/lib/chunkText.js
This is the live text chunker actually used by document upload (`routes/upload.js`), distinct from the dead `ingest/chunkText.js`. It exports `MAX_CHUNKS = 2000`, documented as a deliberate bound on worst-case Ollama embedding calls per document (roughly 1.8M characters at default chunk size, far beyond any legitimate single upload). `chunkText(text, { size, overlap })` normalizes whitespace, splits on paragraph boundaries, further splits any paragraph longer than `size` into sentences, accumulates into chunks with a trailing-overlap carryover between chunks, and filters out any accidental consecutive duplicate chunks.

### backend/src/lib/chunkText.test.js
A small Node test-runner suite for the live chunker above: it asserts blank input produces zero chunks, and that chunking 80 generated sentences with `size: 300, overlap: 40` produces more than two chunks, each within a bounded length (`size + overlap`-ish, checked as `<= 380`).

### backend/src/lib/ocrHelper.js
Live startup helper imported by the live `config.js`: `ensureOcrLanguageFile()` makes sure the Tesseract `eng.traineddata.gz` OCR language file is available in `config.ocrDir`, checking first for a local copy, then a pre-bundled copy shipped alongside the packaged Electron app (handling both source-tree and packaged-build relative paths), and only downloading it from `tessdata.projectnaptha.com` as a last resort — so offline OCR keeps working without any internet access once the file is bundled or already downloaded once.

### backend/src/lib/pluginLoader.js
Live plugin system: `loadPlugins(app)` ensures `config.pluginsDir` exists, reads every `.js` file in it, dynamically `import()`s each one via a `file://` URL, and if the module exports a default function, calls it with the Express `app` instance so a plugin can register its own routes/middleware. Failures to load an individual plugin are caught and logged per-file rather than crashing the whole app.

### backend/src/lib/tokeniser.js
Empty file — contains no code.

### backend/src/lib/validate.js
Live, widely-used input-validation library. It defines `ValidationError` (always carries `.status = 400`, which `app.js`'s generic error handler specifically checks for to decide whether a message is safe to echo to the client), a `scalar()` helper guarding against HTTP Parameter Pollution (Express parsing `?q=a&q=b` as an array rather than a string), and validators `requireString`, `optionalString`, `requireEnum`, and `boundedInt` (which enforces a client-supplied integer stays within a min/max range rather than trusting an arbitrary value like `maxSteps=999999999`). It also exports `requireUuidParam(paramName)`, an Express middleware factory that rejects a route param that isn't UUID-shaped before it reaches any query, built on `validateUuid.js`.

### backend/src/lib/validateUuid.js
A single-purpose live helper: `isValidUuid(value)` checks a string against the canonical UUID regex. Its comment explains why this matters — every id the app hands out is a `crypto.randomUUID()` value, never client-chosen, so any identity-shaped value about to be interpolated into a filesystem path or an unparameterized query (as happens in `vectorService.js`) should be validated against this shape first, closing an audit finding where an unvalidated `userId` reached `path.join` directly.

### backend/src/services/authService.js
The live authentication service backing `routes/auth.js`. It hashes passwords with `crypto.scryptSync` plus a random per-user salt, defines a local `AuthError` class (distinct from `ValidationError`, since login needs a 401 rather than a hardcoded 400) whose messages are safe to show verbatim, and enforces an 8–128 character password length bound (the upper bound exists specifically to stop a multi-megabyte string from making the server spend CPU hashing it). `registerUser`, `loginUser`, `getUserById`, and `changePassword` cover normal account lifecycle, with `changePassword` revoking all existing sessions afterward via `sessionService.revokeAllSessionsForUser`. Password reset is a genuine token-based flow: `requestPasswordReset` generates a random 32-byte token, stores only its SHA-256 hash in `password_resets`, deletes any prior unused token for the account, and writes the raw token to a local file (`password-reset-token.txt`, mode `0600`) in the same storage directory as the database — a deliberate design choice documented as appropriate for a fully offline desktop app with no email infrastructure — while always taking the same code path regardless of whether the username exists, to prevent account enumeration. `resetPasswordWithToken` atomically claims the token via a single `UPDATE ... WHERE usedAt IS NULL AND expiresAt > ?` (avoiding a read-then-write race), and `deleteAccount` removes the user row (cascading to related tables), forces a WAL checkpoint so the on-disk file reflects the deletion immediately, and also removes that user's per-user LanceDB vector-store directory. `updateUserProfile` only ever writes an explicit allowlist of columns (`displayName`, `email`, `department`), intentionally excluding `role`/`permissions` so no API path can let a user self-promote.

### backend/src/services/authService.test.js
A live Node test-runner suite exercising `authService.js` and `sessionService.js` end-to-end against a temporary, isolated SQLite database (set via `APP_DATA_PATH` before the modules load). It covers password correctness/incorrectness, that passwords are never stored in plaintext or logged, unique salts per user, password length policy boundaries, full session lifecycle (creation, expiry, revocation, multi-device logout isolation), authenticated password change (including session revocation), password reset via the real local token file, and end-to-end register→login→session-verify→logout and duplicate-registration regressions.

### backend/src/services/db.js
A tiny live wrapper: it calls `getDb()` from `db/connection.js` once and exports the result as `db`, giving every other live service a simpler `import { db } from './db.js'` rather than each calling `getDb()` themselves. Not a duplicate database — it's the same underlying `better-sqlite3` instance, just re-exported.

### backend/src/services/documentService.js
Live document-extraction service used by the upload flow. `isSupportedDocument` checks a filename's extension against an allowlist (`.pdf`, `.docx`, `.xlsx`, `.csv`, `.txt`, `.md`). `extractDocument(file)` first verifies the file's actual on-disk bytes match its claimed extension — checking magic-number signatures for PDF/DOCX/XLSX (the latter two share the ZIP signature) and rejecting text-extension files containing a NUL byte in the first 4KB — specifically to stop a renamed executable from being processed just because it was given a trusted extension. It then extracts text via `pdf-parse`, `mammoth`, or `read-excel-file` depending on type, formatting XLSX output as one CSV-like block per sheet.

### backend/src/services/documentsStore.js
Live metadata store for uploaded documents, layered on top of `db.js` and `vectorService.js`. `getDocuments`/`appendDocuments` read/upsert rows in the `documents` table; `deleteDocument` removes the metadata row scoped by both `documentId` and `userId`, then calls `vectorService.deleteChunks` to remove the corresponding LanceDB vector chunks.

### backend/src/services/historyService.js
Live chat-history service backing conversations, messages, and folders. `getConversations`/`getMessages` read chats (pinned-first, then most-recently-updated) with their nested messages. `appendHistory` creates a chat row on first message or updates its `updatedAt`, guards against a client-supplied `conversationId` colliding with another user's existing chat (which would otherwise surface a raw SQLite unique-constraint error), inserts the message, and auto-titles a new conversation from its first user message. `updateConversation` supports partial updates (title, folder assignment, pin, bookmark) and specifically verifies a target `folderId` is owned by the caller before allowing reassignment, closing an authorization gap where a folder id from another user could otherwise be attached. `searchChats` does a bounded (`LIMIT 200`) `LIKE`-based search across chat titles and message content, and folder CRUD (`getFolders`/`createFolder`/`updateFolder`/`deleteFolder`) is all scoped by `userId`.

### backend/src/services/memoryService.js
Live, small CRUD service over the `memories` table: `getMemories` (optionally filtered by `type`), `addMemory`, `deleteMemory`, and `clearMemories` (all/by-type), every operation scoped to the given `userId`.

### backend/src/services/ollamaService.js
The live Ollama HTTP client used throughout the real application (distinct from the dead `llm/ollamaClient.js`). `ollamaFetch` wraps every call with a friendlier "Cannot reach Ollama, is it running?" error on network failure. `listInstalledModels`/`listLoadedModels` query `/api/tags` and `/api/ps`; `unloadModel`/`unloadAllModels` free models from memory via `keep_alive: 0`. `embed(texts)` tries the modern batch `/api/embed` endpoint first and falls back to looping the older per-text `/api/embeddings` endpoint if that fails. `streamChat` and `streamGenerate` both stream newline-delimited JSON from `/api/chat`/`/api/generate` respectively, incrementally decoding and invoking `onToken`/`onChunk`/`onToolCall` callbacks as content arrives, with `streamChat` additionally collecting any tool calls the model emits. `parseJson` gives clear, specific error messages for empty or malformed responses from Ollama.

### backend/src/services/passwordReset.test.js
An extensive live Node test-runner suite specifically for the password-reset token flow in `authService.js`, going well beyond `authService.test.js`'s basic coverage: registered-vs-unregistered username handling and enumeration resistance, malformed-input handling, that repeated reset requests invalidate the previous token, token validation (valid, random, missing, tampered, expired), user binding (a token can only ever reset the account it was issued for, proven structurally since the reset function takes no username/userId parameter at all), rejection of an invalid new password without consuming the token, old-password-fails/new-password-works, replay rejection after a successful reset, a genuine concurrency race test asserting exactly one of two simultaneous uses of the same token succeeds, session revocation on reset, and that the raw token is never logged on either the request or the failure path (only safe markers like `PASSWORD_RESET_REQUESTED`/`_SUCCESS`/`_FAILED`).

### backend/src/services/sessionService.js
The live server-side session mechanism, replacing what its own comments describe as a prior scheme where an unsigned `x-user-id` header was the entire authentication mechanism. Sessions are opaque 256-bit random bearer tokens (not JWTs, since revocation/expiry both need a server-side lookup anyway); only the SHA-256 hash (`hashToken`, also reused by `authService.js`'s password-reset flow) is ever persisted, with a 7-day TTL. `createSession` issues and stores a new token; `verifySession` looks it up by hash, deletes and rejects it if expired, and implements sliding expiry — extending the TTL when a session is used past its halfway point, so a stolen-but-unused token still expires on schedule while an actively-used one doesn't die mid-session. `revokeSession` and `revokeAllSessionsForUser` handle single-device logout and full-account revocation (used by password change/reset).

### backend/src/services/speechService.js
Live Windows-only local speech-recognition wrapper. `transcribeLocalWav(audioPath)` throws immediately on any non-`win32` platform, otherwise shells out via `execFile` to a bundled PowerShell script (`scripts/transcribe.ps1`) with a 60-second timeout and a 1MB output buffer cap, parsing the script's JSON stdout for a `text` field.

### backend/src/services/vectorService.js
The live vector-store service backing the app's real RAG/document-search feature, built on `@lancedb/lancedb` — this is what actually replaces the dead `ingest`/`retrieval` pipeline in production. Each user gets a physically separate LanceDB directory (`storage/users/<userId>/lancedb`), opened and cached per-connection by the internal `db(userId)` helper, which re-validates `userId` as a real UUID even though callers are already behind auth middleware, specifically because this value reaches a filesystem path. `indexChunks` embeds text in batches of 16 via `ollamaService.embed` and inserts rows (with a random UUID id, `documentId`, `filename`, `chunkIndex`, `text`, and vector) into a `document_chunks` table, creating it if absent. `searchChunks` embeds the query and runs LanceDB's `vectorSearch`; `listIndexedDocuments` aggregates chunk counts per document. `deleteChunks` documents and works around a specific LanceDB 0.18.2 bug where filtering on the camelCase `documentId` column via a query string silently either throws (unquoted, folded to lowercase by DataFusion) or matches zero rows (quoted) — so it instead fetches all rows client-side, filters by `documentId` in JavaScript, and deletes by the safe lowercase `id` column instead.

### backend/src/services/vectorService.test.js
A live Node test-runner suite specifically proving RAG data isolation between users — flagged in its own comments as a "CRITICAL" audit finding. Since real embedding needs a live Ollama instance the test environment lacks, it seeds fake chunk rows directly via the same `@lancedb/lancedb` client and directory convention `vectorService.js` itself uses, then exercises the real exported functions. It asserts user B sees zero documents (not a filtered view) after only user A has indexed anything, that a raw `vectorSearch` against B's own (nonexistent) table returns nothing even with an identical query vector while the same vector does return the seeded row against A's own connection, that the two users' storage directories are genuinely separate on disk and each only contains that user's own UUID segment, that `deleteChunks` called with another user's document id is a safe no-op that never touches the real owner's data, and that a malformed or path-traversal-shaped `userId` (e.g. `'../../etc/passwd'`) is rejected outright rather than silently treated as a fresh valid store.
## Backend: Training Scripts & Dataset Tools

### backend/finetune/train_chanakya.py

A Colab/GPU fine-tuning script (organized as `# %%` cells for copy-paste into Colab, or runnable end-to-end with `python train_chanakya.py`) that LoRA-fine-tunes `unsloth/Qwen2.5-7B-Instruct-bnb-4bit` on `training.jsonl` using Unsloth + TRL's `SFTTrainer`. It loads the base model 4-bit, attaches LoRA adapters (rank 16, targeting the attention/MLP projection matrices), applies the Qwen2.5 chat template to the `messages` field of each training example, trains for 3 epochs, and finally exports the merged weights to GGUF (`q4_k_m` quantization) for use with Ollama. The file's own docstring documents the pipeline it depends on: `export-training-data.mjs` then `build-balanced-training.mjs` must run first (from `backend/`) to produce the balanced `training.jsonl`, since raw repair-session data vastly outnumbers automation data and would otherwise drown out the automation persona.

### backend/finetune/Modelfile

An Ollama `Modelfile` for loading the fine-tuned GGUF as `chanakya-repair`. It points `FROM` at the downloaded `.gguf` file (filename must be corrected to match), defines the Qwen2.5 ChatML prompt template, sets `temperature 0.1` and `num_ctx 8192`, and gives a `SYSTEM` prompt establishing the "Chanakya-Fix" persona: an autonomous Windows troubleshooting agent that diagnoses with read-only commands first, never runs destructive commands, and bases conclusions only on real command output.

### backend/scripts/add-entries-batch.mjs

A hand-authored batch loader that appends a fixed array of six curated repair scenarios (Wi-Fi power management, SysMain memory growth, folder permissions, Defender toggling itself off, Bluetooth HFP audio profile, and a Windows Update 0x80070020 fix) into both `storage/repair-sessions.json` and `storage/repair-dataset.jsonl`, writing the same record shape `RepairLogger.logSession()` produces so downstream validation and export tooling treat them identically to live-logged sessions. Before writing, it runs every step's command through `classifyCommand()` from `dangerClassifier.js` and refuses to add anything containing a blocked-level command, closing off a path by which unsafe commands could re-enter the training data. It normalizes subdomains through the app's own `normalizeSubdomain()` function and delegates the actual duplicate-checked writes to `dataset-manager.mjs`'s `addEntries`.

### backend/scripts/build-balanced-training.mjs

The final "balancing" stage of the training pipeline: it reads `repair-dataset.jsonl`, `automation-dataset.jsonl`, and `general-dataset.jsonl`, finds the size of the smallest non-empty category, and resamples every category to `floor * RATIO` (default ratio 4) — oversampling (repeating + reshuffling) categories smaller than the target and randomly downsampling categories larger than it — so no single category (typically repair, which vastly outnumbers automation) dominates the fine-tune. The combined, shuffled result is written to `storage/training.jsonl`, which `train_chanakya.py` reads directly.

### backend/scripts/dataset-manager.mjs

The shared low-level library (also runnable as a standalone CLI) for manipulating `.json`/`.jsonl` dataset files: it auto-detects JSON vs JSONL format, computes a canonical string representation of any object for equality comparison (`canonicalize`), extracts a dedup key from an entry via dot-notation field paths with optional case-insensitivity (`getEntryKey`), and exposes `checkDuplicates`, `dedupeFile`, and `addEntries` (which appends only non-duplicate items and reports added/skipped counts) plus a `scanDirectory` helper for recursively finding dataset files. Several other scripts (`add-entries-batch.mjs`, `merge-automation-data.mjs`) import its functions directly rather than shelling out to the CLI. Its CLI supports `check`, `check-dir`, `dedupe`, and `add` subcommands with `--key`, `--output`, `--allow-duplicates`, and `--ignore-case` flags.

### backend/scripts/export-training-data.mjs

The "Data Cleaner" stage: it calls `exportTrainingDataSplit()` from `src/ai/RepairLogger.js` to read the unified session database (merged repair + automation sessions), filters to sessions confirmed working or unreviewed, and writes three separate JSONL files — `repair-dataset.jsonl`, `automation-dataset.jsonl`, and `general-dataset.jsonl` (the last reserved/empty until general-conversation sessions exist) — kept apart specifically so `build-balanced-training.mjs` can control their mixing ratio explicitly rather than inheriting whatever proportion accumulated naturally.

### backend/scripts/fix-subdomains.mjs

A one-off normalization pass over `storage/repair-sessions.json` that repairs two problems introduced by bulk scripts that bypassed `RepairLogger.logSession()` (the only code path that normally calls `normalizeSubdomain()`): free-text subdomain labels that don't match the canonical slugs in `knowledge/subdomains.js`, and an over-assignment of `domain: "windows"` (the classifier's fallback) to sessions a keyword check shows clearly belong elsewhere. It reassigns `domain` only away from the "windows" fallback and only on an unambiguous keyword hit (duplicating, rather than importing, `IntentClassifier.js`'s keyword map to avoid pulling in the LLM client), canonicalizes subdomains via an alias table plus domain-specific overrides, and nulls anything with no canonical slug for its domain. It writes a `.bak` backup before overwriting and supports `--dry-run`.

### backend/scripts/merge-automation-data.mjs

Rebuilds `storage/automation-sessions.json` from a raw external source (Claude Desktop's automation-session outputs, referenced via absolute Windows short-path filenames under `AppData\Local\Packages\...`), mapping each record's `intent` field to a canonical subdomain through a large hardcoded `INTENT_TO_SUBDOMAIN` table (aborting if any intent is unmapped). It re-runs the same `classifyCommand()` blocked-command guard as `add-entries-batch.mjs`, exempting placeholder confirmation-gate steps, and — unlike the additive `addEntries` pattern elsewhere — fully overwrites `automation-sessions.json` each run rather than incrementally merging, because the source file is a growing dataset that gets periodically re-batched and an id-keyed incremental add would leave stale copies in place. It notes in comments that any user feedback attached to automation sessions would be lost by this overwrite (though none has been recorded yet).

### backend/scripts/test-dataset-manager.mjs

A `node:test`-based unit test suite for `dataset-manager.mjs`, covering `isJsonl` format detection, `canonicalize` key-order independence, `getEntryKey` (including dot-notation and `ignoreCase`), and end-to-end `checkDuplicates`/`dedupeFile`/`addEntries` behavior against both temporary `.json` and `.jsonl` fixture files created under a `fs.mkdtempSync` scratch directory that is cleaned up at the end.

### backend/scripts/update-topic-coverage.mjs

Regenerates the derived report `storage/topic-coverage-report.json` from the merged session log (via `getSessions()` in `RepairLogger.js`). For every domain/subdomain pair it computes a `coverageBreakdown` count (with `(unclassified)` for nulled subdomains) and, per domain, quality metrics (`qualityOf`: fraction of sessions with real command output, with a failing step, unresolved count, average steps and summary length). It cross-references the canonical `SUBDOMAINS`/`DOMAINS` taxonomy to surface `thinCoverage` — known subdomains with 3 or fewer examples, i.e. the concrete list of what to generate next — and the top 25 most-covered subdomains. Supports `--dry-run` to print a truncated preview instead of writing.

### backend/scripts/validate-storage.mjs

A structural CI-style checker for every file under `backend/storage/`, run via `node scripts/validate-storage.mjs` with exit code 1 on any problem. Using Ajv (2020 draft, `strict: false`) it JSON-schema-validates `db_store.json` (users/chats/messages/folders/memories/documents) against `dbStore.schema.json`, both `repair-sessions.json` and `automation-sessions.json` against `repairSessions.schema.json`, and each `*-dataset.jsonl` line against `repairDatasetLine.schema.json`. Beyond schema conformance it independently checks for duplicate ids/usernames, unparseable embedded-JSON string fields (guarding against the exact bug that once crashed `/api/agent` and `/api/repair` via an unguarded `JSON.parse` in `authService.js`), and — importantly — that each session's `subdomain` actually belongs to its own `domain` per `SUBDOMAINS`, a cross-field invariant the JSON Schema enum alone cannot express. Repeated identical error shapes are grouped into a single summarized line with a count rather than flooding the output.

### backend/scripts/view-db.mjs

A read-only inspection script for `storage/db.sqlite` (opened via `better-sqlite3` in readonly mode). It prints every table name, dumps the `users` table (username/displayName/role/createdAt), dumps the `sessions` table (with token hashes truncated for display), and finally prints every table's schema via `PRAGMA table_info`. Purely a developer diagnostic tool, not part of the training pipeline.

### backend/scripts/reindex.sh

A tiny bash wrapper intended to be run on a schedule (cron/Task Scheduler/launchd) to keep a vector index in sync with the source database: it `cd`s to the project root and runs `npm run ingest`.

### backend/scripts/transcribe.ps1

A PowerShell script that transcribes a given WAV file to text using the built-in `System.Speech.Recognition.SpeechRecognitionEngine` with a free-dictation grammar. It takes `-AudioPath` as a mandatory parameter, configures silence/babble timeouts, runs `Recognize()` once, and emits a compact JSON object (`{text, confidence}`) to stdout — used as a subprocess by the backend for offline voice input.

### backend/scripts/wakeword.ps1

A long-running PowerShell wake-word listener, also built on `System.Speech.Recognition`. It initializes a `SpeechRecognitionEngine` against the default microphone, builds a `Choices`/`GrammarBuilder` grammar matching "Hey Nova", "Nova", or "Chanakya", and registers an event handler that emits a JSON line (`{event:"wakeword", text, confidence}`) to stdout whenever recognition confidence exceeds 0.35. It starts asynchronous multiple-recognition mode, prints a `{"event":"started"}` line, then loops forever (`Start-Sleep` in a `while($true)`) until the process is killed, at which point it unregisters the event and disposes the recognizer. Falls back gracefully with JSON error messages if `System.Speech` or the microphone is unavailable.

### dataset-tools/reports/make_docx.js

A Node script (using the `docx` npm package) that reads `report_data.json` and renders a formatted Word document, `Windows-Repair-Dataset-Coverage.docx`. It builds a title page, a shaded summary table of entry counts per domain, and then, section by section, a heading per domain followed by a bulleted list of every scenario ("goal") in that domain — essentially a human-readable coverage report for reviewers who don't want to read raw JSON.

### dataset-tools/verification/clean_dataset.py

A Python cleanup pass over `repair-sessions.json`/`repair-dataset.jsonl` that removes "template clone" records — the same scenario duplicated many times with only a minor detail changed (e.g. "(Type 1)...(Type 15)") while commands/stdout/summary stay byte-identical, which would otherwise teach the model to memorize rather than reason. It fingerprints every record by MD5 of `summary + command sequence` (ignoring the goal wording), groups by fingerprint, and keeps only the single most evidence-rich copy per group (ranked by total stdout length, step count, summary length, and presence of a failing step). It also flags (and, with `--drop-empty`, removes) records where every step has empty stdout, since those provide no diagnostic evidence. Runs in audit-only mode by default; `--apply` writes backups (`.<timestamp>.bak`) before rewriting both files and a `cleanup-report.json` summary.

### dataset-tools/verification/fix_taxonomy.py

A Python taxonomy-normalization pass, functionally a Python-side counterpart to `fix-subdomains.mjs` but with its own independent canonicalization tables. It rejects malformed subdomains (too long, ALL-CAPS sentences, empty/null), canonicalizes case/spelling variants via a large `CANON` alias dict, and re-derives a subdomain for anything unusable by regex-matching a big ordered list of `KEYWORD_RULES` (e.g. `DNS`/`nslookup` → `DNS`, `Wi-Fi`/`SSID` → `Wi-Fi`) against the goal+summary+commands text, falling back to a per-domain default. After fixing records in place it regenerates `topic-coverage-report.json` (domain/subdomain breakdown, per-domain quality metrics, thin-coverage list, top subdomains) and rewrites `repair-dataset.jsonl` so the system-prompt text reflects the corrected subdomain. `--apply` writes timestamped backups before overwriting.

### dataset-tools/verification/scale_dataset.py

A synthetic data-generation driver intended to grow the dataset from roughly 1k to 10k–50k entries using an LLM API (Anthropic or OpenAI, selectable via `--provider`), using the existing hand-written entries as few-shot seeds. It walks a large topic matrix of domain × symptom × root-cause-class cells (shuffled, checkpointed to `scale_state.json` so a run can be stopped/resumed), and for each cell prompts the model (with a strict system prompt demanding real, correctly-spelled commands, a specific stated root cause, occasional failing steps, and some "no fix possible" scenarios) to emit a JSON array of new scenarios distinct from a supplied "avoid" list of existing goals in that domain. Generated items are validated (required fields present, known domain, plausible-looking PowerShell/CMD commands via a regex/known-native-command allowlist, minimum goal/summary length) and deduplicated against existing goals using both an exact-match check and a fuzzy `difflib.SequenceMatcher` near-duplicate check with a 4-token prefix index for efficiency. Survivors are appended to both `repair-sessions.json` and `repair-dataset.jsonl` (tagged `"source": "synthetic"` so they can always be filtered back out), with periodic checkpoint writes every ~40 accepted entries. The docstring is explicit that synthetic entries are unverified and should be run through the separate `Verify-Dataset.ps1` afterward.

### dataset-tools/generators/ (25 generator scripts)

`gen.py` through `gen26.py` (there is no `gen1.py` — `gen.py` fills that slot) plus `gen_automation.py`, `gen_automation2.py`, and `gen_automation3.py` share one mechanism. Each defines a Python literal list named `NEW` of tuples — for the repair generators, `(domain, goal, summary, [(command, stdout, stderr), ...], recommendation)`, and for the automation generators a longer tuple additionally carrying `intent`, `subdomain`, `parameters`, `riskLevel`, `verification`, and `rollback` — organized under `# ----` comment-banner sections grouping related scenarios (by domain, error-code family, or theme). A closing block of shared boilerplate then loads the existing `repair-sessions.json`/`repair-dataset.jsonl` (or the automation equivalents), assigns each new record a fresh unique id and a synthetic `createdAt`/`feedback.at` timestamp spaced a few minutes apart starting from a fixed base time, builds the full session-log record (`plan`, `steps` with `blocked:false`/`exitCode:0`/`reason:null` filled in, `resolved:true`, canned `feedback`), and in parallel builds the matching chat-format JSONL line (`system` message naming the domain/subdomain specialization, `user` message = the goal, `assistant` message = summary + a bulleted list of commands used + the recommendation). It appends these to the in-memory data, writes both files back out, and finishes with self-check assertions (no duplicate ids, no duplicate goals/user-prompts) printed to stdout. A few scripts deviate from pure "append new data": `gen5.py` first backfills any dataset-jsonl-only entries into the sessions JSON before adding its own new error-code entries; `gen9.py` has an optional (env-var-gated, `RUN_AUG=1`) second pass that generates reworded phrasing variants of every existing entry; `gen16.py` opens with a `CMD_FIXES` dict correcting specific commands flagged by an earlier verification report before adding new data; `gen21.py` first retrofits a `subdomain` field onto every pre-existing record via keyword rules before adding new spec-compliant records; and `gen26.py` differs mechanically by locating and writing directly into the live project's `backend/storage` folder (via `glob.glob('/sessions/*/mnt/chatbot/backend/storage')`) instead of the local working directory. The automation generators (`gen_automation*.py`) target `automation-sessions.json`/`automation-dataset.jsonl` instead, with system-prompt framing built around `intent`/`parameters` rather than domain/subdomain.

## Frontend: Electron Main Process

The Electron main process is organized around `main.js` as the application entry point, which boots the window, spawns and health-checks the backend, and wires up global shortcuts, clipboard/wakeword listeners, and IPC. Subsystem behavior is owned by `managers/` (window geometry and lifecycle, global shortcuts, clipboard polling, notifications, wake-word detection), while `ipc/` modules translate that behavior into `ipcMain.handle`/`ipcMain.on` channels the renderer can call. `preload.cjs` is the only bridge between the two worlds, using `contextBridge` to expose narrow `window.electronAPI`, `window.sessionAPI`, and `window.toolEngine` objects instead of raw IPC access, and `services/` and `utils/` provide the lower-level helpers (file I/O, screen capture, TTS, path resolution, logging, and the sender-trust check) that the managers and IPC handlers build on. Because the app is a single always-on-top BrowserWindow with no `<webview>` or secondary windows, the codebase treats "is this IPC call really from our own window" as a first-class security property, enforced centrally by `utils/ipcTrust.js` and exercised by two Electron-runtime test files.

### frontend/electron/ipc/auth.ipc.js
Registers three IPC handlers for the in-memory session token: `auth:get-token`, `auth:set-token`, and `auth:clear-token`, all delegating to `services/SessionStore.js`. Every handler first calls `isTrustedSender(event)` and short-circuits to a safe default (`null`/`false`) if the sender isn't the app's own tracked window, with an explicit comment noting `auth:get-token` is treated as the single most sensitive read in the app since it hands back the live session credential. Errors from the store are caught and logged rather than thrown, keeping the renderer-facing contract simple (token, boolean, or null/false).

### frontend/electron/ipc/capture.ipc.js
Registers `capture-screen` and `get-screen-sources`, both thin wrappers around `services/ScreenCapture.js`. Each handler gates on `isTrustedSender(event)` before doing anything, with a comment framing screen capture from an untrusted sender as a silent-surveillance risk deserving the same protection as the tool engine and the session token; an untrusted call gets `null` or `[]` back instead of image/window data.

### frontend/electron/ipc/system.ipc.js
Registers a grab-bag of OS-facing channels: `show-notification` (delegates to `NotificationManager.showNotification`), `tts:speak`/`tts:stop`/`tts:voices` (delegate to `services/TextToSpeech.js`, passing through `text`, `speed`, and `voice`), and `save-file` (delegates to `FileService.saveBase64File` using the main window from `WindowManager.getMainWindow()`). Every handler begins with an `isTrustedSender(event)` check that returns a safe falsy default on failure. A code comment on `tts:speak` explains that only `speed` (a multiplier) is accepted because the underlying `say`/Windows backend has no volume control and was silently dropping anything else that was sent.

### frontend/electron/ipc/tool.ipc.js
Registers a single but critical channel, `tool:execute`, which instantiates a `ToolEngineRouter` (from `../../tools/ToolEngineRouter.js`) and dispatches every request to it, wrapped in `requireTrustedSender` rather than a manual `isTrustedSender` check. A prominent comment identifies this as the highest-privilege IPC channel in the app — the entry point to PowerShell/CMD, process, service, registry, and file access — and stresses that the trust check is an additional independent layer in front of that engine's own schema validation, danger-pattern blocking, and confirmation gating, not a substitute for them. Unhandled exceptions from `toolEngine.dispatch` are caught and returned as a structured `{ success: false, error: { code: 'INTERNAL_ERROR', ... } }` response and logged via `utils/logger.js`.

### frontend/electron/ipc/window.ipc.js
Registers the window-chrome channels used by the custom frameless UI: `window-toggle-expand`, `window-set-ocr-mode`, and `window-set-toolbar-mode` as `ipcMain.handle` calls into `WindowManager`, plus fire-and-forget `ipcMain.on` listeners for `window-drag-start`, `window-drag-move`, `window-drag-end`, `window-resize` (calls `setSize` directly on the tracked main window), `window-minimize`, and `window-close`. Notably, this is the one IPC module that does not perform an `isTrustedSender` check on any of its channels.

### frontend/electron/managers/ClipboardManager.js
Implements simple clipboard-change polling: `startClipboardPolling(sendCallback)` reads `clipboard.readText()` every 1500ms and invokes the callback only when the text is non-empty and has changed since the last poll, guarding the read in a try/catch so a locked clipboard can't crash the interval. `stopClipboardPolling()` clears the interval and resets the module's tracked interval id so polling can be safely restarted.

### frontend/electron/managers/NotificationManager.js
A one-function wrapper (`showNotification(title, body)`) around Electron's native `Notification` API, constructing and immediately showing a notification and logging (not throwing) any failure.

### frontend/electron/managers/ShortcutManager.js
Registers and tears down the app's single global hotkey, `CommandOrControl+Space`, via `registerGlobalShortcuts(onToggleCallback)` (which logs success/failure through `utils/logger.js`) and `unregisterGlobalShortcuts()` (calls `globalShortcut.unregisterAll()`). This is what lets the user summon/dismiss the bubble/chat window from anywhere in the OS.

### frontend/electron/managers/WakewordManager.js
Spawns and manages a PowerShell child process (`wakeword.ps1`, located via `utils/pathHelper.js`'s `getWakewordScriptPath()`) that listens for a voice wake word. `startWakeWordDetector(sendCallback)` launches the process with `windowsHide: true`, parses newline-delimited JSON from stdout, and forwards `{event: "wakeword", ...}` payloads to the callback while logging `{event: "error", ...}` payloads and any stderr output; malformed/partial JSON lines are silently ignored. `killWakeWordDetector()` terminates the tracked process and clears the reference.

### frontend/electron/managers/WindowManager.js
The largest and most security-relevant manager: owns creation and all geometry/state transitions of the app's single `BrowserWindow` (bubble, expanded chat, OCR full-screen, and toolbar/hover modes), including drag handling, edge-snapping, and minimize/close behavior that collapses the window back to bubble form first. `createWindow()` builds the window with `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, and a preload script from `getPreloadPath()`, and — critically — installs a `will-navigate` handler and a `setWindowOpenHandler` that block all in-window navigation and popup creation, redirecting only `http(s)` URLs out to the OS's default browser via `shell.openExternal`. Extensive comments explain the threat model: because chat replies render via ReactMarkdown with no link interception, a link originating from an LLM response (including injected/RAG content) is a realistic way an attacker could otherwise navigate this same privileged window to attacker-controlled content and have the preload script re-inject `window.toolEngine`/`window.sessionAPI` (live session token, Phase 4 PowerShell/CMD/file/registry tools) into it. `getMainWindow()` is the accessor `utils/ipcTrust.js` relies on for its sender check, making this module foundational to that whole trust boundary.

### frontend/electron/preload.cjs
The sole `contextBridge` boundary between renderer and main process, exposing three narrow globals instead of raw `ipcRenderer` access: `window.electronAPI` (screen capture, window toggling/dragging/minimize/close/resize, notifications, wake-word and clipboard change subscriptions, TTS speak/stop/getVoices, OCR/toolbar mode toggles, save-file), `window.sessionAPI` (`getToken`/`setToken`/`clearToken`, mapping to the `auth:*` channels, with a comment noting the token lives only in main-process memory and never touches disk), and `window.toolEngine` (`execute`, `confirm`, `cancel`, `getTools`, and an `onConfirmationRequired` subscription, all funneled through the single `tool:execute` invoke channel with different `tool`/`action` payloads, e.g. `tool: '_system'` for confirm/cancel/getTools). All of these correspond directly to the channel names registered in the various `ipc/*.js` modules.

### frontend/electron/services/BackendHealth.js
Exposes `waitForBackend(url, timeout = 20000)`, which polls a URL with `http.get` every 400ms until it gets a `200` response or the timeout elapses, at which point it rejects with `"Backend did not start in time"`. Used by `main.js` to block app startup until the Node backend server is ready.

### frontend/electron/services/FileService.js
Provides `saveBase64File(parentWindow, name, base64)`, which opens a native `dialog.showSaveDialog` (with overwrite confirmation) scoped to the given parent window, decodes the base64 payload, and writes it to disk with `fs.promises.writeFile`. Returns `{ success: false, cancelled: true }` if the user cancels the dialog, `{ success: true, filePath }` on success, and rethrows (after logging) on I/O failure — this is what backs the `save-file` IPC channel.

### frontend/electron/services/ScreenCapture.js
Wraps Electron's `desktopCapturer`. `captureScreen()` grabs screen and window sources at 1280x720 thumbnail size, picks the primary screen source (preferring an id starting with `"screen:"`), returns its thumbnail as a data URL alongside a filtered list of open window names (excluding the app's own window and generic "Entire Screen"/"Screen 1" entries). `getScreenSources()` returns a lighter-weight list (id, name, small thumbnail) of all sources for source-picker UIs. Both functions log and rethrow on failure; this backs the `capture-screen` and `get-screen-sources` IPC channels.

### frontend/electron/services/SessionStore.js
Holds the live session token in a single module-level variable (`currentToken`), with `getToken`/`setToken`/`clearToken` accessors and no persistence layer whatsoever — a heavily-commented design choice: the token is deliberately never written to disk (no electron-store, no file), so it's cleared on every app restart, and it's kept out of renderer `localStorage` so a future XSS in the renderer couldn't read it directly or find it surviving as a permanent on-disk artifact. This is the backing store for the `auth:*` IPC channels.

### frontend/electron/services/TextToSpeech.js
Implements text-to-speech using the `say` npm package (Windows SAPI under the hood). `getVoices()` lazily queries and caches the list of installed voice names. `speak(text, { voice, speed })` trims and validates the text, stops any in-progress speech, resolves the requested `voice` through `resolveVoice()` — which only allows a voice name that appears in the actual installed-voices list — and then calls `say.speak`. A detailed comment explains why: `say` interpolates the voice name directly into a PowerShell command (`$speak.SelectVoice('<voice>')`), so an arbitrary renderer-supplied string would execute as script, whereas the spoken text itself is safe since it's passed via stdin. `stop()` halts playback and `isSpeaking()` exposes current state; this backs the `tts:speak`/`tts:stop`/`tts:voices` IPC channels.

### frontend/electron/tests/ipcTrust.test.mjs
An Electron-runtime test script (must run under the real `electron` binary, not plain Node, because `node:test`'s scheduler doesn't reliably resolve inside Electron's main-process event loop) that exercises `utils/ipcTrust.js` against a real `WindowManager.createWindow()`-created window rather than a mock. It asserts that the actual tracked window's `webContents` is recognized as trusted, that a second structurally-identical-but-untracked `BrowserWindow`'s `webContents` is not, that `requireTrustedSender` both lets a real handler run for the trusted sender and refuses to run it (returning `{ success: false, error: { code: 'UNTRUSTED_SENDER' } }`) for an untrusted one, and that a destroyed tracked window is never considered trusted even though it was previously the legitimate window. Results are printed as PASS/FAIL lines and the process exits non-zero if any check fails.

### frontend/electron/tests/navigationGuard.test.mjs
Another real-Electron-runtime test (same node:test-incompatibility rationale as above), which reconstructs the exact `will-navigate` and `setWindowOpenHandler` logic from `WindowManager.js` against a throwaway `BrowserWindow` loading a temp fixture HTML file, with `shell.openExternal` monkey-patched to record calls instead of actually opening a browser. It verifies three things: a script-driven `location.href` navigation to an external `https://` URL is prevented (window stays on the original page) while the URL is forwarded to `shell.openExternal`; a `window.open()` call to an external URL never creates a second `BrowserWindow` and is likewise forwarded; and a non-`http(s)` scheme navigation (a `file://` URL) is blocked outright and never forwarded to the system browser at all. Extensive header comments document the same threat model as `WindowManager.js` — LLM-echoed/RAG-injected links being the realistic trigger for an unsolicited navigation of this single privileged window — and explain why this test isn't wired into any existing test runner (the repo has no Electron-level harness).

### frontend/electron/utils/constants.js
Defines shared layout and networking constants: `BUBBLE_SIZE` (80, kept in sync via comment with the rendered `FloatingBubble.jsx` avatar), `CHAT_WIDTH`/`CHAT_HEIGHT` (420x680), `TOOLBAR_HEIGHT` (400, sized to fit the bubble plus five quick-action buttons plus a greeting bubble) and `HOVER_WIDTH` (300), plus `BACKEND_PORT` (3001) and the derived `HEALTH_CHECK_URL` (`http://127.0.0.1:3001/api/health`) used by `BackendHealth.js`.

### frontend/electron/utils/ipcTrust.js
The core of the app's IPC security model: `isTrustedSender(event)` checks that `event.sender` is exactly the single `BrowserWindow`'s `webContents` as tracked by `WindowManager.getMainWindow()`, also verifying that window isn't destroyed. `requireTrustedSender(handler)` is a higher-order wrapper that short-circuits to a standard `{ success: false, error: { code: 'UNTRUSTED_SENDER', message: '...' } }` response instead of invoking the wrapped handler when the check fails. The module's doc comment explains the design rationale: because this app has exactly one legitimate `webContents` for its entire lifetime (no `<webview>`, no `BrowserView`, and — thanks to the Phase 6 navigation guard — no way for the renderer to spawn a second window or navigate this one elsewhere), "trusted sender" collapses to a single equality check, though the comment flags that this would need to become an allowlist if the app ever legitimately grows a second window. This module is what every `isTrustedSender`/`requireTrustedSender` call in `ipc/auth.ipc.js`, `ipc/capture.ipc.js`, `ipc/system.ipc.js`, and `ipc/tool.ipc.js` depends on.

### frontend/electron/utils/logger.js
A minimal logging shim: `logger.log`, `logger.error`, and `logger.warn` each prefix output with `[electron]`/`[electron ERROR]`/`[electron WARNING]` and delegate to the corresponding `console` method. Used throughout the managers, services, and `tool.ipc.js` for consistent, taggable main-process logging.

### frontend/electron/utils/pathHelper.js
Resolves filesystem paths that differ between packaged and development builds. Computes `rootDir` (the `frontend/` directory) from the module's own location, and exposes `isPacked` (from `app.isPackaged`), `getBackendPath()` (backend `server.js`, from `process.resourcesPath` when packaged or a sibling `../backend` directory in dev), `getWakewordScriptPath()` (same packaged-vs-dev logic for `wakeword.ps1`, used by `WakewordManager.js`), and `getPreloadPath()` (always `electron/preload.cjs` under `rootDir`, used by `WindowManager.createWindow()`).
## Frontend: React UI (src/)

The frontend is a React 19 + Vite + Tailwind single-page app wrapped by Electron. `App.jsx` is the root component: it owns the top-level `isExpanded` flag from the shared Zustand store and switches between two lazy-loaded shells — `MainLayout` (the full chat workspace window) when expanded, and `FloatingBubble` (the small draggable avatar widget) when collapsed. `MainLayout` composes `Sidebar`, `Topbar`, `ChatArea`, and `InputArea` into the authenticated workspace, falling back to `LoginScreen` when no user is signed in. Nearly every component reads and writes through `useAppStore.js`, a single flat Zustand store that centralizes auth, chat, documents, memories, settings and avatar signals — there is no React Context or prop-drilling of app state. A parallel "3D avatar" subsystem under `widget/avatar3d/` exists as an opt-in upgrade path for the bubble's 2D photo avatar, driven by a small deterministic state machine (`avatarDirector.js`) rather than LLM calls, but stays inert today because no rigged model file ships with the app. All backend calls go through `services/api.js`, a thin axios/fetch wrapper against a local Node server at `http://127.0.0.1:3001/api`.

### frontend/src/App.jsx
The application root. It reads `isExpanded`, `ocrScreenshot`, `settings.accentColor` and several action creators from `useAppStore`, and on mount calls `checkAuth()` and `fetchModels()` once, plus registers Electron IPC listeners (`onWakewordDetected`, `onClipboardChanged`) when `window.electronAPI` is present — a detected wake word auto-expands the window and shows a native notification, and clipboard text over 3 characters triggers a toast via `showClipboardToast`. Two effects free the local LLM from memory (`unloadIdleModel`) three seconds after the window collapses to the bubble or whenever `document.hidden` becomes true, so idle time doesn't keep VRAM/RAM pinned. It renders either `MainLayout` or `FloatingBubble` (both `React.lazy`), plus the always-present `OcrCropModal` (when a screenshot is pending) and `ConfirmationModal` (for destructive tool-call approvals).

### frontend/src/main.jsx
The Vite/React entry point — mounts `<App />` into `#root` inside `React.StrictMode` and imports the global `styles.css`. No store or API access of its own.

### frontend/src/animations/presets.js
A small constants module of reusable Framer Motion transition configs (`springElastic`, `springSmooth`, `appleBounce`, `glide`, `fade`, `pulse`) used throughout the UI for consistent motion feel. It holds no state and makes no API calls; components simply import `presets` and spread the relevant preset into a `transition` prop.

### frontend/src/chat/ChatArea.jsx
The main content pane, switched by the `activeTab` prop passed down from `MainLayout` (`'chat'`, `'documents'`, `'memories'`, `'diagnostics'`, `'translator'`). For the documents tab it renders a drag-and-drop upload zone and the indexed-file catalog, reading `documents`, `isUploadingDocs`, `uploadProgress` from the store and calling `fetchDocuments`, `uploadDocuments`, `deleteDocument` — upload results are passed through `warnAboutSkippedUploads` from `utils/uploadFeedback.js` to alert on skipped files. For chat it renders either `Welcome` (no active conversation) or `MessageList`; the other tabs simply delegate to `MemoryPanel`, `SystemMonitor`, or `TranslatorPanel`.

### frontend/src/chat/InputArea.jsx
The message composer at the bottom of the chat pane. It owns local UI state (voice/video panel visibility, camera preview, audio source selection) and reads/writes `inputText`, `isGenerating`, `pendingScreenCapture`, `clipboardToastText`, `autoRepairMode`, and `bubbleAction` from the store, calling `sendMessage`, `stopGeneration`, and `uploadDocuments`. It integrates the webcam (via `getUserMedia`) for snapshot capture, Electron's `captureScreen`/OCR IPC calls for screenshots, and embeds `VoiceRecorder` and `ScreenRecorder` as collapsible drawer panels. The Send button either calls `sendMessage(content, capture)` or, mid-generation, `stopGeneration()`; a toggle switches "Auto-Repair" mode which changes the placeholder text and routes messages through the store's autonomous repair agent instead of normal chat.

### frontend/src/chat/MessageList.jsx
Renders the scrolling transcript for `activeMessages` from the store, auto-scrolling to the bottom only while the user is already near it (tracked via a scroll-distance ref) so reading history during streaming isn't yanked away. It renders assistant messages through `ReactMarkdown`, shows RAG source chips when a message carries `sources`, and offers per-message copy/speak actions (speak uses the raw browser `SpeechSynthesisUtterance` rather than the shared `services/speak.js` helper). A text-selection listener shows a floating "Explain"/"Summarize" toolbar that stuffs the selected text into `setInputText`. ### frontend/src/chat/Welcome.jsx
The empty-chat landing screen shown when there's no active conversation. It reads `documents` and `settings` from the store, shows a knowledge-base summary banner when documents exist, and renders three suggested-prompt cards; clicking any of them or the "Summarize knowledge base" link calls the `onPrompt` callback passed down from `ChatArea`, which in turn calls `sendMessage`.

### frontend/src/components/ChanakyaAvatar.jsx
A small presentational component used on the login screen: a circular avatar that swaps between `chanakya_default.png` and `chanakya_hover.png` on mouse hover, with a pulsing radial-gradient aura behind it. Takes only an `accentColor` prop; no store or API access.

### frontend/src/components/ConfirmationModal.jsx
A blocking modal rendered globally by `App.jsx` whenever `pendingConfirmations` in the store is non-empty (populated when a native system tool call, e.g. registry or PowerShell, requires explicit user approval). It shows the oldest pending confirmation's message and calls `resolveConfirmation(confirmationId, true|false)` on Allow/Cancel, which resumes or cancels execution via `window.toolEngine`.

### frontend/src/components/LoginScreen.jsx
The sign-in/register/password-reset form shown by `MainLayout` when no user is authenticated. It manages all form state locally and calls `login`, `register`, `requestPasswordReset`, and `resetPasswordWithToken` from the store, which in turn hit `/auth/login`, `/auth/register`, `/auth/forgot-password`, and `/auth/reset-password` via `services/api.js`. Client-side validation mirrors the backend's password/username length rules so invalid input is caught immediately rather than round-tripping for a generic 400. It embeds `ChanakyaAvatar` for branding.

### frontend/src/components/MainLayout.jsx
The authenticated app shell. Reads `user`, `isAuthLoading`, and `settings` from the store; shows a "Checking session..." placeholder while `isAuthLoading` is true (since the session token lives in the Electron main process, not localStorage, and must be fetched asynchronously), then `LoginScreen` if still unauthenticated, or the full workspace (`Sidebar` + `Topbar` + `ChatArea` + conditionally `InputArea`) otherwise. It also implements custom window-resize drag handles that call `window.electronAPI.resize(w, h)` for the borderless Electron window, and applies glassmorphism styling driven by `settings.transparency`/`windowOpacity`/`theme`.

### frontend/src/components/Topbar.jsx
The header bar above the chat area. Reads/writes `models`, `selectedModelId`, `selectedAgentProfile`, `metrics`, and `settings` from the store, polling `fetchMetrics()` every 3 seconds for a hover-revealed CPU/RAM/GPU/disk/tokens-per-second popover. It renders dropdowns for choosing the local Ollama model and the "agent persona" (default/coder/writer/analyst — a client-side label only, no separate backend endpoint), plus custom window controls (minimize, collapse-to-bubble, close) that call `window.electronAPI.minimize()`/`close()` and the store's `collapseToBubble()`/`toggleExpand()`. It also implements the draggable-titlebar behavior via `window.electronAPI.dragStart/dragMove/dragEnd`.

### frontend/src/dashboard/SystemMonitor.jsx
The "Diagnostics" tab content — a read-only dashboard of CPU/RAM/GPU/disk meters and AI inference stats (tokens/sec, first-token latency, process memory), all sourced from the store's `metrics` object via `fetchMetrics()` polled every 2 seconds. Also displays static text describing the offline stack (Ollama, LanceDB/SQLite). No writes to the store beyond the poll.

### frontend/src/hooks/useSpeech.js
A React hook providing microphone-based speech-to-text plus text-to-speech, with two engines: the browser's native Web Speech API when available (never inside Electron, since it needs Google's servers) and a local Whisper model (`@huggingface/transformers`, `Xenova/whisper-tiny.en`, WebGPU with WASM fallback) otherwise, with a final server fallback that POSTs a WAV blob to `/transcribe` (`api.post('/transcribe', ...)` via `lib/api.js`, a note: this uses a different import path than the rest of the app's `services/api.js`). It exposes `{ listening, transcribing, audioLevel, toggleListening, speak, isModelReady }`. `speak()` delegates to `services/speak.js`. This hook does not appear to be used by any of the primary chat components (which use `VoiceRecorder` + `services/transcriber.js` instead) but is available as an alternative speech integration point.

### frontend/src/memory/MemoryPanel.jsx
The "AI Memories" tab. Reads `memories`, `isMemoriesLoading`, `settings` from the store; on mount calls `fetchMemories()`. Lets the user add a new fact/instruction (project- or general-scoped) via `addMemory(content, type)`, delete individual entries via `deleteMemory(id)`, and wipe everything via `clearMemories()` (behind a native `confirm()`). These map to the backend's `/memory` CRUD endpoints in `services/api.js`.

### frontend/src/profile/ProfileDetails.jsx
A portal-rendered modal (opened from `Sidebar`) showing the signed-in user's profile: display name, role/department, and workspace stats (`conversations.length`, `folders.length`, `documents.length`, `memories.length`, all pulled straight from the store). It includes an inline "Change Password" form (`changePassword(currentPassword, newPassword)`, hitting `/auth/change-password`) and a "Delete Account" danger-zone form requiring password confirmation plus an acknowledgement checkbox (`deleteAccount(password)`, hitting `DELETE /auth/account`).

### frontend/src/screen/OcrCropModal.jsx
A full-screen screenshot annotation and OCR tool, shown by `App.jsx` whenever `ocrScreenshot` is set in the store. It offers four tools (crop-for-OCR, freehand draw, rectangle outline, text label) drawn onto a transparent `<canvas>` overlaid on the captured image. "Extract Text" crops the selection to a temp canvas and runs `Tesseract.recognize` (client-side, `langPath` pointed at the local backend's `/ocr` static path) then calls the `onSuccess(text)` callback passed from `App.jsx`, which stuffs the text into `setInputText` and expands the window. "Send image to AI" instead composites all markups onto the full image and stores the resulting data URL via `setPendingScreenCapture`, closing the modal and expanding the window. State touched: `ocrScreenshot`, `isOcrProcessing`, `setPendingScreenCapture`, `toggleExpand`, `isExpanded`.

### frontend/src/screen/ScreenRecorder.jsx
A screen/window video recorder panel embedded in `InputArea`'s drawer. It calls `window.electronAPI.getScreenSources()` to list capture targets, then uses `navigator.mediaDevices.getUserMedia` with Electron's `chromeMediaSource: 'desktop'` constraint and a `MediaRecorder` (VP9/webm) to record. After stopping, it offers "Save Local" (base64-encodes the blob and calls `window.electronAPI.saveFile()`, with a completion `showNotification`) or "Index to AI" (wraps the blob as a `File` and calls the store's `uploadDocuments` + `fetchDocuments`, indexing the recording into the RAG knowledge base).

### frontend/src/services/api.js
The central axios/fetch wrapper and the single source of truth for the backend base URL: `const API_BASE = 'http://127.0.0.1:3001/api'`. It manages the session token via `window.sessionAPI` (an Electron IPC bridge to the main process, deliberately not localStorage, to avoid XSS exposure and disk persistence) with an in-memory fallback for non-Electron dev. An axios instance (`api`) auto-attaches the bearer token on every request and, on any 401, clears the session and dispatches a `chanakya:session-expired` window event (which the store listens for to force logout). `streamChat()` and the shared `streamNdjson()` helper (used by `streamRepair`/`streamAgent`) hand-roll `fetch()`-based newline-delimited-JSON stream readers for `/chat`, `/repair`, and `/agent`. Exported endpoint groups: `auth` (`/auth/login`, `/register`, `/logout`, `/me`, `/profile`, `/change-password`, `/account` delete, `/forgot-password`, `/reset-password`), `history` (`/history`, `/history/search`, `/history/:id`, `/history/folders`), `documents` (`/documents`, `/upload` with a 600s timeout, `/documents/:id` delete), `models` (`/models`, `/models/loaded`, `/models/unload`), `memories` (`/memory` CRUD), `transcribe` (`/transcribe`), `stats` (`/stats`), `translate` (`/translate`, 200s timeout), and `repair` (`/repair/feedback`, `/repair/sessions`, `/repair/dataset`).

### frontend/src/services/speak.js
A text-to-speech helper solving the "silent utterance" problem in Electron: `speechSynthesis.getVoices()` loads asynchronously, so `speak()` waits for the voice list (with a 1.5s giveup) before speaking, and prefers `window.electronAPI.speak()` (the native Windows TTS engine, since Chromium's own engine reports zero voices under Electron) before falling back to the Web Speech API, picking the best-sounding available English voice. Returns a Promise that resolves once speech actually finishes. Also exports `stopSpeaking()`. No store or backend API access — pure browser/Electron IPC.

### frontend/src/services/toolEngine.js
A thin SDK class (`ToolEngineSDK`, exported as singleton `toolEngine`) wrapping `window.toolEngine`, the Electron preload bridge to native system tools. Exposes `execute(tool, action, params)`, convenience per-service methods (`file`, `powershell`, `cmd`, `services`, `registry`, `hardware`, `process`, `network`), `confirm`/`cancel` for gated destructive actions, `getTools()` to enumerate available actions, and a confirmation-required event subscription (`onConfirmationRequired`) used by the store to populate `pendingConfirmations`.

### frontend/src/services/transcriber.js
Speech-to-text used by `VoiceRecorder`: loads a local Whisper pipeline (`@huggingface/transformers`, `Xenova/whisper-tiny.en`, WebGPU then WASM fallback, cached as a singleton promise), transcribes recorded audio via `blobToPcm16k`/`encodeWav` from `wav.js`, and falls back to POSTing a WAV to the backend's `/transcribe` (Windows Speech Recognition) via `services/api.js` when Whisper fails to load. Exposes `warmUpTranscriber()` (prefetch) and `transcribe(recording)` returning `{ text, engine }`.

### frontend/src/services/wav.js
Low-level audio utilities: `resampleTo16k` (linear-interpolation resampler to the 16kHz rate the Windows speech engine expects), `encodeWav` (raw PCM → WAV blob), `toMono` (channel averaging), `blobToPcm16k` (decodes any MediaRecorder blob via `AudioContext.decodeAudioData` and returns 16kHz mono samples), and `blobToWav`. Pure audio processing, no store or network access — consumed by both `services/transcriber.js` and `hooks/useSpeech.js`.

### frontend/src/settings/SettingsModal.jsx
The preferences modal opened from `Sidebar`. Reads/writes `settings` via the store's `updateSetting(key, value)` (which also persists each value to `localStorage` under a `chanakya-*` key). Controls exposed: dark/light theme, glassmorphism transparency + window opacity slider, accent color picker (five presets), Framer animation toggle, and a "spoken hover greeting" toggle that gates whether `FloatingBubble` calls `speak()`.

### frontend/src/sidebar/Sidebar.jsx
The collapsible left navigation rail. Reads `user`, `conversations`, `folders`, `activeChatId`, and `settings` from the store, calling `fetchHistory()` on mount and offering navigation buttons for chat/documents/memories/diagnostics/translator tabs (via the `setActiveTab` prop from `MainLayout`). It renders pinned, bookmarked, and folder-grouped conversation lists with inline rename/delete/pin/bookmark/move-to-folder actions (`renameChat`, `deleteChat`, `pinChat`, `bookmarkChat`, `moveChatToFolder`, plus `createFolder`/`renameFolder`/`deleteFolder`), all backed by the store's `/history` and `/history/folders` API calls. It also embeds `SettingsModal` and `ProfileDetails` as modals opened from footer buttons, and calls `logout()`.

### frontend/src/stores/useAppStore.js
The single Zustand store backing almost the entire app (932 lines, no slicing/combining — one flat `create((set, get) => ({...}))`). Its state divides into: **auth** (`user`, `isAuthLoading`, plus `login`/`register`/`logout`/`checkAuth`/`changePassword`/`deleteAccount`/password-reset actions, all via `services/api.js`'s `auth` group, with the session token persisted through Electron IPC rather than localStorage); **window/UI mode** (`isExpanded`, `toggleExpand`/`collapseToBubble`, synced with Electron's window-resize IPC); **avatar signals** (`micListening`, `avatarSpeaking`, `bubbleAction` — real events, not LLM-driven, consumed by the widget's `avatarDirector`); **chat** (`activeChatId`, `activeMessages`, `isGenerating`, `activeSources`, `conversations`, `folders`, and the core `sendMessage()` action, which runs a full ReAct tool-calling loop against `streamChat()`, dispatching detected tool calls through `window.toolEngine`, handling confirmation-gated actions via `pendingConfirmations`, and streaming tokens into the active assistant message); **auto-repair mode** (`autoRepairMode`, `_streamAutoRepair()` which streams NDJSON events from `/repair` into a formatted markdown transcript, and `pendingRepairFeedback`/`submitRepairFeedback` for the "did it work" prompt); **documents** (`documents`, `isUploadingDocs`, `uploadProgress`, `fetchDocuments`/`uploadDocuments`/`deleteDocument`); **memories** (`memories`, `fetchMemories`/`addMemory`/`deleteMemory`/`clearMemories`); **models** (`models`, `selectedModelId` persisted to localStorage, `fetchModels`/`selectModel`/`unloadIdleModel`); **metrics** (`metrics` object polled via `fetchMetrics`); and **settings** (theme, transparency, accent color, animations, voice greeting — each individually persisted to localStorage via `updateSetting`). It also listens globally for a `chanakya:session-expired` window event (dispatched by `services/api.js` on any 401) and calls `logout()` in response.

### frontend/src/utils/uploadFeedback.js
A single exported helper, `warnAboutSkippedUploads(result)`, that inspects a document-upload API response's `skipped` array and shows a native `alert()` summarizing which files were indexed vs. skipped and why — used by `ChatArea`, `InputArea`, and indirectly documents-related flows so a folder upload where every file happens to be unsupported doesn't look like a silent no-op.

### frontend/src/voice/VoiceRecorder.jsx
The mic-recording panel embedded in `InputArea`'s voice drawer. Captures audio via `getUserMedia` (mic, or Electron desktop-audio loopback when `audioSource === 'system'`), draws a live frequency-bar waveform on a `<canvas>` via a Web Audio `AnalyserNode`, and on stop transcribes the recording using `services/transcriber.js`'s `transcribe()`. It mirrors recording state into the store via `setMicListening` (a sibling — the avatar widget — reacts to that flag rather than the two being parent/child), and calls `onTranscription(text)` on success, which `InputArea` appends into `inputText`.

### frontend/src/widget/FloatingBubble.jsx
The collapsed-mode floating avatar widget (683 lines) — the always-on-top small Electron window's content when `isExpanded` is false. Reads `settings`, `user`, `micListening`, `isGenerating`, `avatarSpeaking` from the store and computes `avatarDirector.deriveAvatarState(...)` each render to drive visual mood (glow color, head-tilt keyframes, gaze offset) purely from those real signals. Implements: a magnetic cursor-pull effect and eye-tracking pupil offset (via Framer Motion springs); a hover-triggered speech-bubble greeting (`greetings.js`'s `nextLine`) that's optionally spoken aloud through `services/speak.js` (rate-limited by a 6s cooldown, gated by `settings.voiceGreeting`); a quick-actions toolbar (mic, capture screen, OCR, record, minimize) that appears on hover, calling `window.electronAPI.captureScreen()`/`setToolbarMode()`/`dragStart/Move/End` and store actions (`setOcrScreenshot`, `setPendingScreenCapture`, `setBubbleAction`, `toggleExpand`). A click (as opposed to a drag) on the bubble calls `toggleExpand()` to open the full chat window. It lazily imports `avatar3d/AvatarScene.jsx`, which stays inert (falls back instantly, `onFallback`) until a real `.glb`/`.fbx` model file exists on disk, in which case the 2D photo fades out in favor of the 3D render.

### frontend/src/widget/avatar3d/AvatarScene.jsx
Mounts a `@react-three/fiber` `<Canvas>` scene and, inside it, `RpmAvatar` pointed at `GLB_MODEL_URL` (`./avatar3d/character.glb`), but only if WebGL is supported. If the model fails to load (the expected default state, since no model ships with the app) it calls `onFallback()` so `FloatingBubble` stays on the 2D photo avatar; on success it calls `onReady()`. Accepts the `avatarState` object from `avatarDirector.deriveAvatarState()` as a prop, passed straight through to `RpmAvatar`.

### frontend/src/widget/avatar3d/ProceduralAvatar.jsx
An alternative, currently-unused 3D avatar built entirely from primitive Three.js geometry and a hand-authored bone hierarchy (head/neck/shoulders/elbows as nested `Group`s) rather than any imported model file — a fallback design explicitly noted as superseded by the RPM/glTF path in `AvatarScene.jsx`. Drives breathing, head turn/tilt/nod (matching `avatarDirector`'s `headMovement`/`eyeFocus`), blinking, a talking-mouth pulse, and a timed wave gesture, all computed per-frame in `useFrame` from `avatarState` and an `accent` color prop.

### frontend/src/widget/avatar3d/RpmAvatar.jsx
Mounts a loaded Ready Player Me (or any glTF) character via `rpmLoader.js`'s `loadGlbCharacter(url)`, adding its root object into the R3F scene graph. Per-frame (`useFrame`) it applies gentle idle sway/breathing to the whole model and drives blink/talking-mouth via whatever ARKit-style morph targets the model actually shipped with (`setMorph(BLINK_NAMES/MOUTH_OPEN_NAMES, value)`), reading blink timing constants from `avatarDirector.js` and the `lipSync`/`breathing` fields of the `avatarState` prop. Deliberately does not attempt bone-based limb/head animation, since guessing bone names across arbitrary RPM exports is fragile.

### frontend/src/widget/avatar3d/animationMap.js
A pure data module mapping `avatarDirector` states/gestures to Mixamo animation clip filenames expected under `public/avatar3d/` (`BASE_MODEL_URL`, `CLIP_URLS`, `ANIMATION_FOR_STATE`, `ANIMATION_FOR_GESTURE`). None of the referenced files need to exist for the app to run — `mixamoLoader.js` skips missing clips gracefully. No component in the current codebase imports this against a live Mixamo character (the active path is the RPM/glTF morph-target one), so it functions as a prepared-but-unused integration point.

### frontend/src/widget/avatar3d/mixamoLoader.js
A loader for a Mixamo-rigged character (`loadMixamoCharacter({ baseUrl, clipUrls })`) using Three.js's `FBXLoader`. It existence-checks each URL via `HEAD` request before parsing (to distinguish "missing file" from an opaque parse error), builds an `AnimationMixer` with cross-fade `play(name)` support, and skips any clip that 404s rather than failing the whole character load. Companion to `animationMap.js`; not currently wired into `AvatarScene.jsx` (which uses the RPM/glTF path instead).

### frontend/src/widget/avatar3d/rpmLoader.js
Loads a Ready Player Me/glTF character (`loadGlbCharacter(url)`) via Three.js's `GLTFLoader`, again existence-checking the URL first. It scans all meshes for `morphTargetDictionary`/`morphTargetInfluences` and exposes `setMorph(names, value)`, which sets the first matching morph target name (from `BLINK_NAMES`/`MOUTH_OPEN_NAMES` candidate lists) across every mesh that has it — this is what `RpmAvatar.jsx` calls each frame for blink and talk animation. This is the active model-loading path used by `AvatarScene.jsx`.

### frontend/src/widget/avatarDirector.js
A pure, dependency-free state machine: `deriveAvatarState(signals)` takes real app booleans (`isListening`, `isThinking`, `isSpeaking`, `justGreeted`, `hasError`) and returns a full `AvatarDirectorState` object (state name, emotion, emotion intensity, gesture, head movement, eye focus, lip-sync flag, blink flag, breathing rate, animation speed). Priority order is error > speaking > listening > thinking > idle. Also exports blink timing constants (`BLINK_INTERVAL_MS`, `BLINK_DURATION_MS`) shared by both the 2D (`FloatingBubble.jsx`) and 3D (`RpmAvatar.jsx`/`ProceduralAvatar.jsx`) renderers. Explicitly documents that the current 2D avatar assets are flat photographs, so only a subset of the full state contract (breathing/blink as CSS pulses, head movement as rotate/translate, emotion as glow color, lip-sync as a pulsing ring, gesture as a badge icon) is actually renderable today — the rest is a stable target for a future rigged asset.

### frontend/src/widget/greetings.js
Pure helper functions for the bubble's hover speech-bubble text: `firstNameOf(user)` extracts a capitalized first name from `displayName`/`username`; `openingLine(name)` builds a time-of-day-aware first greeting ("Good morning, Alex. How can I help?"); `capabilityLine(previous)` picks a random line from a fixed pool of ~10 short capability blurbs (Wi-Fi repair, document Q&A, screen reading, etc.), avoiding immediate repeats; and `nextLine({ isFirstHover, displayName, previous })` is the single entry point `FloatingBubble.jsx` calls to pick which line to show. No store or API access.
## Frontend: Local Tool-Execution Engine & Build Config

The `frontend/tools/` tree is a self-contained "tool engine" that runs in the Electron main process and gives the Chanakya AI assistant the ability to actually act on the user's Windows machine — running PowerShell/CMD, touching the filesystem, the registry, Windows services, processes, and network diagnostics. Every request flows through one gate before real system access happens: `ToolEngineRouter` dispatches a `{tool, action, params}` request to the matching `*Service.js`, which first runs `InputValidator` against a declared schema, then — if the action is marked `destructive` — routes through `ConfirmationGate` to force an explicit user confirmation before anything runs; PowerShell/CMD/process-launch paths additionally pass every command string through `dangerGuard.isBlockedCommand()` both before and after confirmation, and several services layer their own hard-coded protected-target checks (system paths, registry autostart keys, security-service names, critical PIDs) that cannot be bypassed by confirming.

### frontend/tools/BaseToolService.js
This is the abstract base class every tool service (`FileService`, `PowerShellService`, etc.) extends, and it defines the actual gate mechanics: `execute()` looks up the action, validates params via `InputValidator`, and — if the action's config sets `destructive: true` — stops short of running the handler and instead calls `ConfirmationGate.request()` to register a pending confirmation and return a `needsConfirmation` response to the caller. `executeConfirmed()` is the twin entry point used after the user approves, which skips the destructive check and calls the handler directly — meaning any safety check that isn't re-run inside the handler itself (as `dangerGuard` deliberately is) would be bypassed on this path. Notably, `_requestConfirmation()` builds the human-facing prompt by calling an optional `getConfirmationMessage(action, params)` hook that specific services define to show the *real* target (the actual command text, path, or service name) rather than a generic static description — the file's own comments note this wiring was previously dead code, so confirmation dialogs used to show only "Execute a PowerShell command" with no way for a user to see what they were actually approving.

### frontend/tools/ConfirmationGate.js
A small in-memory store of pending confirmations, keyed by a random UUID (`crypto.randomUUID()`), each with a 60-second auto-expiry timer. `request()` registers a new pending entry and metadata (tool/action/params); `confirm()` and `cancel()` resolve or reject the corresponding entry and remove it, so a confirmation id can only be used once. This is the sole mechanism standing between a "please confirm" prompt and actual execution of a destructive action — if this expires or the id doesn't match, `ToolEngineRouter` returns a `CONFIRMATION_FAILED` error rather than running anything. A code comment notes a fix where the internal promise is given a no-op `.catch()` so that an unawaited rejection (every timeout or cancel) doesn't crash the Node process via an unhandled rejection.

### frontend/tools/InputValidator.js
A dependency-free schema validator supporting `string`, `number`, `boolean`, `enum`, `path`, `array`, and `object` types, used by `BaseToolService.execute()` to reject malformed parameters before any handler runs. Its `path` type is particularly security-relevant: `validatePath()` requires an absolute Windows path (drive-letter or UNC prefix), rejects `..` traversal sequences, and rejects characters like `<>"|?*` and control characters — this is the first line of defense for every `FileService` action that takes a `path` parameter, though it only validates path *shape*, not which specific paths are safe to write/delete (that's handled separately by `FileService`'s own protected-path check).

### frontend/tools/ToolEngineRouter.js
The central dispatcher: it instantiates one shared `ConfirmationGate` and all eight tool services (`file`, `powershell`, `cmd`, `services`, `registry`, `hardware`, `process`, `network`) and routes incoming `{tool, action, params}` requests to the right one, or to special `_system` handling for `confirm`/`cancel`/`getTools`. On `_system.confirm`, it resolves the pending entry via the gate and then calls `executeConfirmed()` on the originally-targeted service — this is the only path by which a destructive action actually executes, and it explicitly re-validates that the confirmation id is real and unexpired rather than trusting the caller. It also exposes `getTools()`, which returns the full action registry (including which actions are `destructive`) to the renderer for building the model's tool schema — meaning the list of what the AI is even allowed to attempt is generated from this same registry.

### frontend/tools/dangerGuard.js
A standalone regex blocklist, `isBlockedCommand()`, checked against raw command/script text for PowerShell and CMD execution paths. It flags irreversible or session-disrupting operations that must never run *even after user confirmation* — disk formatting/partitioning (`format-volume`, `diskpart`, `remove-partition`), recursive deletion of Windows/System32, deleting local users or adding new admin accounts, disabling Windows Defender or the firewall, `Set-ExecutionPolicy` bypass, download-and-execute one-liners (`iwr | iex`), deleting/stopping services via `sc delete`/`Remove-Service`, writing to registry Run keys, and rebooting/shutting down the machine or killing core OS processes (`lsass`, `winlogon`, etc.). The module's docstring notes it mirrors an equivalent `BLOCKED_PATTERNS` list in `backend/src/agent/dangerClassifier.js`, kept as a separate duplicate because this tree packages independently — so the two lists can drift out of sync if one is updated without the other.

### frontend/tools/services/CmdService.js
Wraps direct Windows Command Prompt execution (`cmd.exe /c <command>`) and batch-file execution (`.bat`/`.cmd`), both marked `destructive: true`, so both require a `ConfirmationGate` confirmation showing the literal command or script path before running. Beyond confirmation, `runCmd()` and `executeBatch()` both call `dangerGuard.isBlockedCommand()` — on the raw command text for `execute`, and on the batch file's *file contents* (read and checked up to 2MB) for `executeBatch` — specifically because a confirmation dialog only shows a file path, not what's inside it, so without this content check a confirmed batch file could silently contain a blocked, catastrophic command. Output is captured via `child_process.spawn` with a configurable timeout (default 30s) and truncated to 20,000 characters to bound memory.

### frontend/tools/services/FileService.js
Wraps general filesystem access: reading/writing files (10MB read cap), listing/searching directories, copying, moving, and deleting files, plus an `open` action that resolves and launches an arbitrary file, folder, URL, or installed application by name (via a bundled PowerShell resolver script using App Paths registry lookups and `Get-StartApps`). `writeFile`, `deleteFile`, `copyFile`, and `moveFile` are all `destructive: true` and confirmation-gated (a code comment notes `copyFile` was previously miscategorized as non-destructive despite silently overwriting existing files); `writeFile`/`deleteFile`/`copyFile`/`moveFile` additionally call `assertNotProtectedPath()`, which hard-blocks any resolved path under `C:\Windows\` regardless of confirmation. The `open` action is deliberately non-destructive for UX speed, but this created a real bypass: launching "powershell" or "cmd" via `open` would previously start an interactive shell instantly with no confirmation and no `dangerGuard` check — this is now closed by `assertNotShellLaunch()`, which refuses `open` requests targeting shell aliases (`cmd`, `powershell`, `pwsh`, `wt`, etc.), forcing shell access through the properly-gated `PowerShellService`/`CmdService` instead.

### frontend/tools/services/HardwareService.js
A read-only service exposing system/hardware telemetry — hostname, CPU/memory usage, disk info, GPU info, battery status, and network adapter configuration — combining Node's `os` module with PowerShell `Get-CimInstance` queries. Every action here has `destructive: false`, so none of it goes through `ConfirmationGate` or `dangerGuard`; this is appropriate since nothing it does mutates system state, though it does shell out to `powershell.exe` for several queries.

### frontend/tools/services/NetworkService.js
A read-only network diagnostics service: `ping`, `traceroute`, DNS lookup, TCP port scanning (up to 100 ports, checked directly via `net.createConnection` rather than shelling out), `netstat`-style connection listing via PowerShell, full IP configuration, and a basic HTTP reachability/speed test. All actions are `destructive: false` and unconfirmed, but host/hostname inputs are explicitly validated by a local `validateHost()` against an injection-character blocklist and a hostname/IP shape regex before being passed to `execFile('ping'/'tracert', ...)`, which prevents shell-metacharacter injection into those subprocess calls even though the actions themselves are non-destructive.

### frontend/tools/services/PowerShellService.js
The core PowerShell execution service: `execute` runs an arbitrary command string and `executeScript` runs a `.ps1` file by path, both `destructive: true` and confirmation-gated with a message showing the literal command/script path. Critically, both `runPS()` (for `execute`) and `executeScript()` call `dangerGuard.isBlockedCommand()` — the former on the raw command text, the latter by reading the script file's content (up to 2MB) and scanning it — and this check runs on the confirmed execution path itself (inside the handler), not just at request time, so it cannot be skipped by going through `executeConfirmed()`. A code comment states this check was previously dead code — `dangerGuard`'s own docstring claimed it ran post-confirmation, but nothing actually called it until this was wired in, and `executeScript` in particular had no content check at all, letting a confirmed script silently contain any blocked, catastrophic command. `getVersion` is non-destructive and unconfirmed.

### frontend/tools/services/ProcessService.js
Lists, inspects, kills, and starts OS processes: `list`/`getProcess` are read-only (via PowerShell `Get-Process`), while `kill` (via `taskkill /PID`) and `startProcess` (via `child_process.spawn`) are `destructive: true` and confirmation-gated showing the PID or full command line. Beyond confirmation, `kill()` resolves the PID to a process name first and refuses (`PROTECTED_PROCESS` error) if it matches a hard-coded critical-system-process list (`wininit`, `csrss`, `winlogon`, `services`, `lsass`, `smss`, `system`, `ntoskrnl`) — killing any of these can crash or lock the whole session, and this check runs even on the confirmed path. `startProcess()` is especially notable: because it launches an arbitrary executable+args directly, it was a silent bypass of every other PowerShell/CMD guard (e.g. calling `startProcess('powershell.exe', ['-Command', '<dangerous>'])` skipped `PowerShellService`'s confirmation and blocklist entirely) — this is now closed by running `dangerGuard.isBlockedCommand()` against the joined command+args string before spawning.

### frontend/tools/services/RegistryService.js
Wraps `reg.exe` for reading, writing, deleting, and listing Windows Registry keys/values. `getValue`/`listKeys`/`keyExists` are non-destructive; `setValue` and `deleteValue` are `destructive: true` and confirmation-gated, showing the exact key path, value name, and (for `setValue`) the data being written. All key paths are validated to start with a real hive (`HKLM`, `HKCU`, etc.) and value/data strings are checked against an injection-character blocklist before being passed as `reg.exe` arguments. Beyond that, `setValue`/`deleteValue` call `assertNotProtectedKey()`, which hard-blocks writes/deletes (`PROTECTED_REGISTRY_KEY` error, regardless of confirmation) to a fixed list of sensitive subtrees: the Run/RunOnce autostart keys, Winlogon Shell/Userinit, Windows Defender policy, the LSA, Image File Execution Options (a known debugger-hijack technique), and SafeBoot — a comment notes that prior to this, any key inside HKLM/HKCU could be written once past the basic hive-format check.

### frontend/tools/services/WinServicesService.js
Manages Windows services via PowerShell `Get-Service`/`Start-Service`/`Stop-Service`/`Restart-Service`. `list` and `getStatus` are read-only; `start`, `stop`, and `restart` are `destructive: true` and confirmation-gated with the specific service name shown. Service names are sanitized against a strict alphanumeric/dot/dash/underscore pattern before being interpolated into PowerShell command strings. `stop`/`restart` additionally call `_assertNotProtected()`, which hard-refuses (`PROTECTED_SERVICE` error, regardless of confirmation) a fixed set of security-critical services — Windows Defender (`WinDefend`, `MpsSvc`, `Sense`, `wscsvc`, `SecurityHealthService`), Windows Update (`wuauserv`), and the Event Log (`EventLog`) — since stopping any of these blinds the machine to malware or removes forensic visibility.

### frontend/tools/tests/test-services.js
A minimal manual smoke-test script (not a `node:test` suite) that instantiates all eight services against a shared `ConfirmationGate` and runs a handful of sanity checks — `HardwareService.systemInfo`, `FileService.listDir`, a validation-error case, confirming `CmdService.execute` correctly requires confirmation, and `WinServicesService.list` — printing pass/fail to the console and exiting non-zero on failure.

### frontend/tools/tests/toolEngine.security.test.js
A substantial `node:test`-based security regression suite (362 lines) that directly exercises the real gate logic rather than mocks, documenting and testing fixes from a security audit referenced in its header comments: confirmation messages showing actual targets instead of generic text, `dangerGuard` actually being wired into the confirmed-execution path for both `PowerShellService` and `CmdService`, `executeScript`/`executeBatch` content-scanning bypasses, `ProcessService.startProcess`'s lack of a policy check, `FileService.open`'s shell-launch bypass, `ProcessService.kill`'s critical-process protection (verified against a real resolved `lsass.exe` PID where possible), `WinServicesService`'s protected-service list, `RegistryService`'s protected-key list, `FileService`'s protected-path checks and `copyFile`'s destructive reclassification, and `ToolEngineRouter`'s rejection of spoofed/unknown tool and action names and reuse of stale confirmation ids. It's effectively the living specification of every hard-coded safety boundary described above, and is the best single file to read to understand exactly what is and isn't blocked.

### frontend/vite.config.js
The Vite build configuration for the React frontend: it enables the `@vitejs/plugin-react` plugin, sets `base: './'` (relative asset paths, needed for the app to load correctly when packaged into an Electron `file://` context), and configures a dev-server proxy forwarding `/api` requests to `http://127.0.0.1:3001`, where the local backend runs during development.

### frontend/tailwind.config.js
A standard Tailwind CSS config scoping content scanning to `index.html` and `src/**/*.{js,jsx}`, extending the default theme with the app's custom dark "ink" color palette and a "gold" accent palette (used for the Chanakya branding), a matching gold box-shadow glow, and custom sans/serif font stacks (Inter/Segoe UI and Georgia).

### frontend/postcss.config.js
A one-line PostCSS config that simply enables the `tailwindcss` and `autoprefixer` plugins, wiring Tailwind's utility generation and vendor-prefixing into the build pipeline.
