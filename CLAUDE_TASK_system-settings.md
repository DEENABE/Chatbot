# Task: Windows Settings, Control Panel & system tools — open support

Implement "open" support for Windows Settings pages, Control Panel applets, MMC consoles and built-in
system tools in the generic app agent. **Scope = OPEN + VERIFY only.** Do NOT implement changing settings
(dark mode toggle, bluetooth on/off, volume etc.) in this task — that is a later phase.

Work only in the source tree:
- `frontend/tools/**` (tool engine: discovery, resolver, launch, verification)
- `backend/src/orchestrator/**` (only if routing needs a change)

Do NOT hand-edit `frontend/backend-runtime/**` or `frontend/release-*/**` — they are generated by
`frontend/scripts/prepare-backend.cjs` / electron-builder.

Keep the existing security model intact: code-owned launchers only, `shell:false`, no user text ever
becomes an executable path or argument, `validateTarget` / `trustedSystemCapability` stay the single
trust gate, sensitive items never auto-open on fuzzy match.

---

## Current state (verified by reading the code)

1. `frontend/tools/apps/WindowsSystemCapabilityRegistry.js` defines `systemCapabilities()` (13 entries:
   Control Panel, Settings, Bluetooth Settings, Device Manager, Services, Task Manager …) but it is
   **never merged into the registry**. It is only used by `trustedSystemCapability()` as a trust check.
   So `resolver.resolve("device manager", registry.apps)` cannot find it. `AppDiscoveryService.discover()`
   also skips any discovered row whose exe is `explorer|control|mmc|regedit|taskmgr`.
2. Only 2 `ms-settings:` URIs exist (`ms-settings:` and `ms-settings:bluetooth`).
3. `Get-StartApps` in `DiscoverApps.ps1` also returns a "Settings" AUMID entry
   (`windows.immersivecontrolpanel_...!microsoft.windows.immersivecontrolpanel`). If the system "Settings"
   capability is merged naively, `AppResolverService.resolve` sees two EXACT matches → `AMBIGUOUS_APP`.
4. `ProcessService.observeSystemApp` (≈line 58) and `UIAutomationService` (≈line 21) decide the expected
   process by `app.id.includes('settings')` → `SystemSettings` / `ApplicationFrameHost`. Every new
   Settings page id MUST end with `-settings` so this keeps working without changes.
5. `validateTarget` in `AppTargetPolicy.js` calls `trustedSystemCapability(app)` first; for
   `source==='windows_management'` it requires `mmc.exe` + one `System32\*.msc` arg.

- Registry refresh must still succeed when `DiscoverApps.ps1` fails partially (system capabilities are

## Step 3 — Control Panel applets (dynamic discovery, no product list)

In `DiscoverApps.ps1` add source `control_panel`:
- Enumerate `HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\ControlPanel\NameSpace\*`.
- For each CLSID read `Registry::HKEY_CLASSES_ROOT\CLSID\{clsid}`: `System.ApplicationName`
  (canonical, e.g. `Microsoft.ProgramsAndFeatures`) and `LocalizedString` / `(default)` for display name.
- Resolve `@dll,-id` indirect strings via `SHLoadIndirectString` (Add-Type P/Invoke, shlwapi.dll).
  Skip entries whose name can't be resolved.
- Emit rows only when canonical matches `^Microsoft\.[A-Za-z]+$`.

In JS (`AppDiscoveryService`): map to `launchType:'windows_system_command'`,
`executablePath: %SystemRoot%\System32\control.exe`, `launchArgs:['/name', canonical]`,
`windowTitle: displayName`. Add `'control_panel'` to allowed sources in `AppTargetPolicy.js`.
Extend `trustedSystemCapability` with a branch that accepts ONLY: exe == System32\control.exe,
exactly 2 args, `args[0]==='/name'`, `args[1]` matches `^Microsoft\.[A-Za-z]+$`.
Verification: window of process `explorer` whose title contains the display name
(extend `observeSystemApp` names logic for source `control_panel`).
Mark `Microsoft.AdministrativeTools`, `Microsoft.UserAccounts`, `Microsoft.CredentialManager`,
`Microsoft.BitLockerDriveEncryption`, `Microsoft.WindowsFirewall` as `resolutionRisk:'sensitive'`
(this is a risk list, not a discovery list — acceptable).

## Step 7 — Packaging (the built installer must contain everything)

How packaging works today (verified):
- `frontend/package.json` `build.files` includes `tools/**/*` → any new JS under `frontend/tools` ships automatically.
- `.ps1` + `DesktopAccessibility.cs` from `tools/apps` go to `resources/desktop-control` via `extraResources`.
- `backend/src` → `scripts/prepare-backend.cjs` → `frontend/backend-runtime` → `afterPack.cjs` copies to `resources/backend`.

Required:
1. Prefer extending the existing `DiscoverApps.ps1`. If you add ANY new `.ps1`/`.cs` helper, you MUST also add it to
   `DESKTOP_HELPERS` in `tools/DesktopRuntime.js` (else `helperScriptPath` throws `DESKTOP_HELPER_NOT_ALLOWED` at runtime)
   and to the helper list in `scripts/validate-security-package.cjs`. If it is not `*.ps1` or the `.cs` file, update the
   `extraResources` filter too.
2. Add the new/changed trust-critical files to the integrity `files` list in `scripts/validate-security-package.cjs`:
   `tools/apps/SettingsCatalog.js`, `tools/apps/WindowsSystemCapabilityRegistry.js`, `tools/apps/AppTargetPolicy.js`,
   `tools/apps/AppDiscoveryService.js`, `tools/apps/AppRegistryService.js`.
3. Build with `npm run electron:release -w frontend` (NOT `npm run build`, which only builds Vite). It must end with
   "Clean Windows security release validated". Then smoke-test the unpacked app in `frontend/release-security/win-unpacked`:
   "open wifi settings", "open device manager", "open control panel", "open windows features".
